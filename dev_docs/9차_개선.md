# 9차 개선 — 답변 제공처를 떼어내고, Gemini를 실제로 찔러 봄

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · [3차 개선](3차_개선.md) · [4차 개선](4차_개선.md) · [5차 개선](5차_개선.md) · [6차 개선](6차_개선.md) · [7차 개선](7차_개선.md) · [8차 개선](8차_개선.md) · **9차 개선** · [평가 질문](평가_질문.md)

8차에서 배포까지 끝낸 뒤 남은 일은 품질 개선뿐이었습니다. 이번에는 **"답변 모델을 좀 더
메이저한 것으로 바꿀 수 있나"**에서 출발했습니다. 후보는 Gemini Flash였습니다.

결과를 먼저 적습니다. **쓰고 싶었던 `gemini-3.8-flash`는 무료 티어에서 호출 자체가 안
됩니다**(13번 중 1번 성공). 대신 **한 급 아래인 `gemini-3.5-flash-lite`가 뜻밖에 좋았고**,
8차에서 모델을 바꾸며 잃었던 3·8번을 되찾으면서 11번을 지켰습니다. 다만 각 1회씩만 쟀으므로
확정은 아닙니다.

그리고 모델을 갈아끼워 보려다 **설정 구조의 문제**를 먼저 만났습니다. 그 쪽이 이번 회차에서
실제로 코드에 남은 변경입니다.

| | 8차까지 | 9차 |
| --- | --- | --- |
| 답변 제공처 설정 | 임베딩과 같은 `rag.cloudflare.*` 하나 | **`rag.chat.*` 로 분리** (기본값은 Cloudflare) |
| 모델 이름 | `application-prod.yml`에 고정 | `CHAT_MODEL` 환경변수로도 받음 |
| 기동 로그 | `Cloudflare 스트리밍 사용: model=…` | `답변 제공처: host=…, model=…, maxTokens=…` |
| 제공처 바꾸는 방법 | YAML을 고치고 다시 빌드 | **`.env` 세 줄** (`CHAT_BASE_URL`·`CHAT_API_KEY`·`CHAT_MODEL`) |

## 1. 왜 설정을 먼저 쪼갰나

`application-prod.yml`은 답변과 임베딩이 **같은 값 하나**를 보고 있었습니다.

```yaml
spring.ai.openai.base-url: ${rag.cloudflare.base-url}   # 답변
spring.ai.openai.api-key:  ${rag.cloudflare.api-token}
# 임베딩도 같은 rag.cloudflare.* 를 CloudflareEmbeddingModel이 직접 읽는다
```

8차에서는 이게 장점이었습니다 — 제공처가 하나라 키도 base-url도 하나였습니다. 그런데 **두
값의 제약이 다릅니다.**

- **임베딩은 못 바꿉니다.** 적재된 819청크가 `bge-m3` 1024차원 벡터 공간에 묶여 있습니다.
  바꾸면 전체 재적재 + 임계값 재측정입니다.
- **답변은 바꿀 수 있습니다.** 측정 숫자에 따라 갈아끼우는 것이 8차 §3④의 남은 일이었습니다.

그래서 **바꿀 수 있는 쪽만 제공처 중립적인 이름으로 뽑아냈습니다.** 임베딩 쪽은
`rag.cloudflare.*` 이름을 그대로 뒀습니다 — Cloudflare 고정이라는 사실이 이름에 드러나는
편이 맞습니다.

```yaml
rag:
  chat:
    base-url: ${CHAT_BASE_URL:${rag.cloudflare.base-url}}
    api-key:  ${CHAT_API_KEY:${rag.cloudflare.api-token}}
```

기본값이 임베딩 쪽을 가리키므로 **아무것도 주지 않으면 8차 구성 그대로**입니다. Render
대시보드에는 `CHAT_*`이 없으니 배포는 영향을 받지 않습니다.

### 핵심은 YAML이 아니라 스트리머였다

`spring.ai.openai.*`만 바꿔도 절반밖에 안 됩니다. **배포 스트리밍은 Spring AI를 타지 않기
때문입니다**(8차 §6). `CloudflareChatStreamer`가 `rag.cloudflare.base-url`을 직접 읽고
있었으므로, 그대로 두면 이런 상태가 됩니다.

- 비스트리밍(`/api/ask`, 측정 하네스가 쓰는 길) → 새 제공처
- 스트리밍(`/api/ask/stream`, 화면이 쓰는 길) → **여전히 Cloudflare**

**화면과 측정이 서로 다른 제공처로 도는 사고**입니다. 스트리머도 `rag.chat.*`을 읽게
바꿨습니다. 클래스 주석에는 "설정 키는 제공처 중립이지만 이 파서는 Cloudflare 응답을
전제로 한다"는 경고를 남겼습니다.

### 기동 로그를 한 줄 바꿨다

```
답변 제공처: host=api.cloudflare.com, model=@cf/meta/llama-3.3-70b-instruct-fp8-fast, maxTokens=400
```

`Cloudflare 스트리밍 사용: model=…`을 이걸로 갈았습니다(문서에서 참조하지 않는 줄이라
안전합니다). **제공처와 모델이 어긋난 상태는 로그에 안 찍히면 알아채기 어렵습니다.** 키는
찍지 않고 host만 찍습니다. 실제로 이 로그가 뒤에서 한 번 일을 했습니다 — 아래 함정 ②입니다.

### 함정 ① 빈 문자열은 기본값을 못 부른다

`.env`에 `CHAT_BASE_URL=`을 **빈 값으로 두면 안 됩니다.** placeholder의 기본값은 키가
**없을 때만** 걸리고, 빈 문자열은 "값이 있음"으로 읽혀서 base-url이 빈 채로 기동합니다.
`.env.example`에는 `#CHAT_BASE_URL=`처럼 줄 자체를 주석 처리해 뒀습니다.

### 함정 ② 모델 이름이 같이 움직이지 않았다

처음 분리에서 base-url과 키만 뽑고 **모델 이름은 YAML에 두었습니다.** 그 상태로 `.env`에
Gemini 키를 넣고 띄우니, **Gemini 호스트에 Cloudflare 모델 이름**(`@cf/meta/llama-…`)이
날아갔습니다. 기동 로그가 바로 보여 줬습니다.

```
답변 제공처: host=generativelanguage.googleapis.com, model=@cf/meta/llama-3.3-70b-instruct-fp8-fast
```

세 값은 함께 움직여야 하는 한 묶음입니다. 모델도 환경변수로 받게 했습니다.

```yaml
model: "${CHAT_MODEL:@cf/meta/llama-3.3-70b-instruct-fp8-fast}"
```

### 확인한 것

| 조건 | 결과 |
| --- | --- |
| `CHAT_*` 없음 | `host=api.cloudflare.com` · SSE 200 / 3.97초 / 답변 정상 |
| `CHAT_*` 셋 지정 | `host=generativelanguage.googleapis.com, model=gemini-3.5-flash-lite` · 답변 정상 |
| 양쪽 모두 | `Cloudflare 임베딩 사용: model=@cf/baai/bge-m3, dimensions=1024` — 영향 없음 |

`CHAT_*`을 비우면 동작은 8차와 같습니다.

## 2. Gemini를 쓸 수 있는 조건 (공식 문서)

무료만 쓰는 제약(`CLAUDE.md` §6)이 있으니 **무료로 되는 선을 먼저 확인**했습니다.

| 항목 | 확인 결과 |
| --- | --- |
| 가격 | `gemini-3.8-flash`·`3.6-flash`·`3.5-flash-lite`·`3.1-flash-lite`·`2.5-flash-lite` 등이 "Free of charge" |
| 지역 | 한국 지원 |
| 의존성 | **추가 불필요** — `https://generativelanguage.googleapis.com/v1beta/openai/`가 OpenAI 호환 (chat completions·streaming 지원) |
| 카드 | 불필요 |
| 데이터 | **무료 티어는 요청을 Google 제품 개선에 씁니다** (가격 페이지가 "Content used to improve our products: Yes") |

의존성이 필요 없다는 것이 큰 이점입니다. 8차에서 Cloudflare를 붙일 때와 같은 방식 —
`spring-ai-starter-model-openai`에 base-url만 돌려 끼우면 됩니다.

### 돈이 새는 길이 하나 있다

키를 만들 때 **Cloud 프로젝트를 고르게 합니다.** 여기서 두 문장이 중요합니다.

- **"Rate limits are applied per project, not per API key."** 한도는 키가 아니라 프로젝트
  단위입니다. 그 프로젝트에서 도는 다른 것이 있으면 한도를 나눠 씁니다.
- **Tier 1(유료)의 자격이 "set up and link an active billing account"입니다.** 즉 **결제
  계정이 연결된 프로젝트를 고르면 그 순간 유료 티어**가 되고, 문서는 "Free → Tier 1 전환은
  즉시 적용된다"고 적고 있습니다.

그래서 **결제가 붙지 않은 프로젝트**를 골라야 합니다. Firebase 프로젝트는 Blaze 플랜이면
결제가 연결돼 있어 위험합니다. 이번에는 결제 없는 프로젝트로 발급해 무료 등급을 확인했습니다.

### 한도는 계정 화면에서 본다

공식 rate-limits 페이지는 모델별 무료 수치를 전부 싣지 않고(확인된 것은
`Gemini Omni Flash`가 무료 "Not supported", `Gemini Decision 1`이 200 RPM / 50,000 TPM /
10,000 RPD 둘뿐) **계정 화면으로 넘깁니다.**

> View your active rate limits in AI Studio — <https://aistudio.google.com/rate-limit?timeRange=last-28-days>

제3자 보고는 `3.8-flash`를 5 RPM / 20 RPD, Flash-Lite를 15 RPM / 500 RPD로 적고 있지만
**블로그 근거라 확정이 아닙니다.** 이 회차에서는 확정하지 못했습니다.

## 3. 실측 — `3.8-flash`는 무료 티어에서 못 쓴다

2026-11-14, 발급한 키로 직접 호출했습니다. 모델 목록(`GET /models`)은 200으로 64개를 돌려
주고, `gemini-3.8-flash`도 목록에 있습니다. 그런데 **호출이 안 됩니다.**

| 시도 | 결과 |
| --- | --- |
| `max_tokens` 없이 `"hi"` | 4번 중 1번만 200 (나머지 45초 무응답) |
| `max_tokens` 400 | 503 `UNAVAILABLE` |
| `max_tokens` 2000 | 503 `UNAVAILABLE` |
| 5회 연속 (`max_tokens` 400) | **0/5** — 503 두 번, 45초 무응답 세 번 |
| 앱의 실제 프롬프트 | 120초 무응답 |

**합계 13번 시도 중 1번 성공.** 에러 문구는 이렇습니다.

```json
{"error":{"code":503,
  "message":"This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later.",
  "status":"UNAVAILABLE"}}
```

처음에는 `max_tokens`를 의심했습니다 — 성공한 1회가 `max_tokens` 없는 호출이었기 때문입니다.
그래서 `max_tokens`를 뺀 채로 3번 더 쳤고 **3번 모두 무응답**이었습니다. **`max_tokens`와
무관한 용량 문제**입니다.

**OpenRouter를 버린 이유와 같은 공용 풀 혼잡입니다**(8차 §7: `temporarily rate-limited
upstream` 429). 이름만 429에서 503으로 바뀌었습니다. 일일 한도에 걸린 것이 아니라 **호출
자체가 닿지 않습니다.**

덧붙여 `gemini-2.5-flash`는 404입니다 — `"This model is no longer available to new users"`.
8차 시점의 모델 이름이 지금은 신규 사용자에게 안 열립니다.

### 걱정했던 "사고 토큰" 문제는 확인조차 못 했다

고르기 전에 가장 경계한 것은 이것이었습니다. `gemini-3.7`·`3.8-flash`는 **사고(thinking)를
끌 수 없고 최소가 `low`**입니다(`reasoning_effort`에 `none`·`minimal`을 주면 거부하고 `low`로
올립니다). 그리고 Gemini는 사고 토큰이 `max_tokens` 안에서 소비됩니다.

이 프로젝트는 **똑같은 이유로 모델 둘을 이미 탈락시켰습니다** — `qwen3-30b`와 `gemma-4-26b`가
400토큰을 내부 사고에 다 쓰고 본문이 비었습니다(8차 §7, "추론형 모델은 쓰지 않는다").
`3.8-flash`도 구조적으로 같은 위험이었는데, **호출이 안 돼서 재 보지도 못했습니다.**

## 4. `gemini-3.5-flash-lite` — 5/5, 그리고 성적이 좋다

같은 조건으로 Flash-Lite를 쳤습니다.

| 모델 | 5회 시도 | 응답 시간 |
| --- | --- | --- |
| `gemini-3.8-flash` | **0/5** | 45초 타임아웃 / 503 |
| `gemini-3.5-flash-lite` | **5/5 (200)** | 1.76 ~ 2.97초 |

응답에 `finish_reason: "stop"`, 본문 정상, `usage`에 사고 토큰이 예산을 먹은 흔적이 없습니다.

그래서 **앱의 실제 프롬프트와 실제 조각**으로 평가 질문을 돌렸습니다. prod 프로필을 8081에
띄워(IntelliJ의 로컬 앱은 8080에 그대로 두고) `/api/ask`로 쟀습니다.

| 문항 | 유형 | `exaone3.5:2.4b` (로컬) | `llama-3.3-70b` (현 배포) | `gemini-3.5-flash-lite` |
| --- | --- | --- | --- | --- |
| 3 | 프로퍼티 차이 | 정답 | 깨짐 | **정답** |
| 6 | 목록 나열 | 정답 | 정답 | **정답** |
| 7 | 게시판 설치 | 정답 | 깨짐 | 실패 |
| 8 | IDE 설치 | 정답 | 깨짐 | **정답** |
| 10 | 틀린 전제 | 실패 | 실패 (5개를 지어냄) | 실패 (거부) |
| 11 | 할루시네이션 함정 | 0/3 | 3/3 | **통과** |
| 12 | 설명이 붙는 문제 | 설명 붙음 | 미측정 | **깨끗** |

**8차에서 모델을 바꾸며 잃었던 3·8번이 돌아오고, 가장 어렵게 얻은 11번을 지켰습니다.**
7번만 깨진 채로 남았습니다.

- **10번은 여덟 번째 후보도 실패**입니다. 다만 성격이 다릅니다 — `llama-3.3-70b`는 없는
  서비스 그룹 5개를 **날조**했고, Flash-Lite는 "문서에서 찾을 수 없습니다"로 **거부**했습니다.
  오답이지만 안전한 쪽의 오답입니다. `qwen3-30b`와 같은 양상입니다.
- **12번은 §6의 미결 항목이었습니다.** "`exaone3.5:2.4b`의 성향이고 새 모델로는 아직 안
  쟀다"고 남아 있었는데, 설명 없이 깨끗하게 나왔습니다.
- 응답 시간은 **1.2 ~ 2.2초**입니다. 현 배포 `llama-3.3-70b`가 3.1 ~ 4.0초입니다.

**각 1회씩만 쟀습니다.** 이 프로젝트 규칙은 "1회 성공을 해결로 적지 않는다"(4차 교훈)이므로
**후보 신호일 뿐 결론이 아닙니다.** 확정은 `evalReport` 3회 라운드입니다.

### 스트리밍은 기존 파서가 그대로 읽는다

`CloudflareChatStreamer`는 Cloudflare 응답을 전제로 손으로 붙인 것이라, 다른 제공처에서
깨질 수 있다고 봤습니다. 실제로는 그대로 돌았습니다.

| 질문 | 델타 | 총 시간 |
| --- | --- | --- |
| 6번 (짧은 목록) | 1개 | 1.19초 |
| 3번 (긴 설명) | 5개 | 1.32초 |

Cloudflare보다 조각이 굵습니다(Cloudflare는 7~14개). 다만 전체가 1.3초라 체감에는 의미가
없습니다. **어댑터를 새로 붙일 필요는 없습니다.** 대신 Gemini는 규격을 지킬 가능성이 높으니,
채택한다면 **Spring AI 스트리밍으로 되돌릴 수 있는지 먼저 확인해야 합니다** — 손으로 붙인
어댑터는 Spring AI로 안 되는 것이 확인됐을 때만 쓰는 것이 이 프로젝트 규칙입니다.

## 5. 측정을 돌리기 전에 풀어야 할 것

Flash-Lite로 `evalReport` 한 라운드를 돌리려면 두 가지가 걸립니다.

**① 한도 수치를 아직 모릅니다.** 위 AI Studio 화면의 `gemini-3.5-flash-lite` 행에서
RPM·TPM·RPD 셋을 봐야 합니다.

**② 하네스에 호출 간격이 없습니다.** `EvalReportTest`는 질문을 연달아 쏩니다. Ollama는 한
건에 30초였으니 문제가 된 적이 없었는데, Flash-Lite는 2초라 **분당 약 30건**이 나갑니다.
우리 프롬프트는 한 건에 입력 약 1,350 + 출력 400 ≈ **1,750토큰**입니다.

| 한도 | 33콜 라운드에서 | 판정 |
| --- | --- | --- |
| RPD 500 | 33건 | 여유 |
| RPD 20 | 33건 | 초과 — 라운드를 쪼개야 함 |
| RPM 15 | 분당 30건 | 초과 — 간격 필요 |
| TPM 50,000 | 분당 약 52,500토큰 | 초과 |

**분당 15건으로 늦추면 RPM 15와 TPM 50,000을 둘 다 통과합니다**(15 × 1,750 = 26,250).
호출 사이에 3초를 넣으면 되고 라운드가 100초쯤 길어질 뿐입니다.

429가 터져도 보고서를 통째로 잃지는 않습니다 — 하네스가 문항별로 예외를 잡아
`요청 실패: …`로 남기고 계속 돕니다. 다만 그 문항이 "모델 실패"처럼 보여 비교가 흐려집니다.

**비용은 들지 않습니다.** Gemini 무료 티어라 Cloudflare 뉴런을 쓰지 않습니다 — 측정
한 라운드 약 3,200뉴런이라는 8차의 계산이 이 후보에는 해당하지 않습니다.

## 6. 곁에서 발견한 것 — keep-alive 크론이 멈춘 것 같다

배포 상태를 확인하다 걸렸습니다. **2026-11-14 22:42에 보낸 첫 요청이 75.5초**였습니다.
콜드 스타트, 즉 앱이 자고 있었습니다.

크론은 `0,10,20,30,40,50 9-23 * * *` (Asia/Seoul)이라 22:40에 핑이 갔어야 하고, 10분 간격
핑이 닿고 있었다면 애초에 잠들 수 없습니다. **핑이 Render까지 닿지 않고 있다**는 뜻입니다.

8차 §7에 적어 둔 구조가 그대로 의심됩니다 — 기동이 51초 이상인데 cron-job.org는 30초만
기다리므로 실패로 찍히기 쉽고, 연속 실패가 쌓이면 작업이 꺼집니다. 다만 **대시보드를 보지
않고는 확정할 수 없어 여기서는 관찰로만 남깁니다.** Supabase는 7일 저활동이면 일시정지되므로
방치하면 둘이 같이 죽습니다(10월에 한 번 겪었습니다).

깔끔한 재확인은 **낮 시간대에 15분 이상 아무도 건드리지 않은 상태에서 첫 요청을 재 보는
것**입니다. 그때도 1분이 넘으면 크론이 죽은 것이 확정입니다.
