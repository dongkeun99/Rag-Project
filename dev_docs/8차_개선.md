# 8차 개선 — 호스팅에 올리고, 답변 모델을 숫자로 확정함

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · [3차 개선](3차_개선.md) · [4차 개선](4차_개선.md) · [5차 개선](5차_개선.md) · [6차 개선](6차_개선.md) · [7차 개선](7차_개선.md) · **8차 개선** · [평가 질문](평가_질문.md)

7차까지는 전부 제 노트북 안에서 돌았습니다. 남은 목표가 **배포 하나**였고, 이번에 끝냈습니다.
주소는 <https://rag-zxay.onrender.com> 입니다.

배포는 "어디에 올릴까"를 고르는 일이 아니었습니다. **로컬에서 당연하던 전제가 하나씩 무너지는
과정**이었습니다 — 문서가 있던 폴더가 없어지고, DB가 네트워크 너머로 가고, LLM이 남의 API가
되고, 그 API의 응답 규격이 라이브러리가 기대하는 것과 미묘하게 달랐습니다. 그리고 마지막
것은 **화면에서 질문해 보기 전까지 드러나지 않았습니다.**

| | 7차까지 | 8차 |
| --- | --- | --- |
| 실행 위치 | 로컬 전용 | Render 무료 플랜 (0.1 CPU / 512MB) |
| DB | Docker 컨테이너 `rag-postgres` | 로컬은 그대로, 배포는 Supabase (서울) |
| 답변 모델 | `exaone3.5:2.4b` (Ollama) | 로컬은 그대로, 배포는 `llama-3.3-70b` (Cloudflare Workers AI) |
| 임베딩 | `bge-m3` (Ollama) | **같은 `bge-m3`** (Cloudflare) — 적재된 819청크를 그대로 씀 |
| 문서 위치 | `D:/dev/rag-docs` | jar 안 `classpath:docs` |
| 답변 한 건 | 40~170초 | **1~4초** |
| 비용 | 0원 | **0원** (전부 무료 티어) |

## 1. 모델 이름이 같다고 벡터가 같지는 않다

가장 먼저 잰 것이 이것입니다. 배포 계획 전체가 여기서 갈리기 때문입니다.

적재된 819청크를 그대로 쓰려면 Cloudflare의 `bge-m3`가 로컬 Ollama의 `bge-m3`와 **같은 벡터
공간**이어야 합니다. 제공처마다 양자화·정규화·풀링이 다르면 모델 이름이 같아도 값이 어긋나고,
그러면 5차에서 측정으로 정한 `similarity-threshold: 0.50`이 통째로 무효가 됩니다.

재는 방법을 바꾼 것이 핵심입니다. "문장 하나를 양쪽에 넣어 비교"가 아니라 **적재된 벡터를 DB에서
직접 꺼내** 같은 청크 본문의 Cloudflare 임베딩과 비교했습니다. 실제로 지켜야 하는 것이 "저장된
819청크를 그대로 쓸 수 있는가"였기 때문입니다.

| 청크 8개 | 저장벡터 ↔ Cloudflare | 저장벡터 ↔ Ollama 재생성(대조군) |
| --- | --- | --- |
| 평균 | **0.99998** | 1.00000 |
| 최저 | **0.99988** | 1.00000 |

대조군을 같이 잰 이유가 있습니다. 저장벡터 ↔ Ollama가 1.00000이어야 **측정 자체를 믿을 수**
있습니다. 점수만 같고 순위가 흔들려도 의미가 없으니 질문 4개로 상위 8조각까지 대조했는데 **네
질문 모두 순서가 동일**했고 1위 점수 차는 최대 0.0004였습니다. 무관한 질문("오늘 점심 메뉴
추천해줘")도 로컬 0.4714 → 배포 0.4716으로 **여전히 0.50 아래**였습니다.

결론은 **재적재 없음, 임계값 유지**였습니다.

## 2. 로컬에서 당연하던 것들

### 문서 폴더가 사라진다

`rag.docs-path`가 `D:/dev/rag-docs`였습니다. 배포 환경에 그런 경로는 없습니다.
`IngestService`를 `Path`·`Files`에서 Spring `Resource`로 바꿔 파일시스템과 jar 안을 같은 코드로
읽게 하고, md 54개(556KB)를 `src/main/resources/docs/`에 넣었습니다.

함정이 하나 있었습니다. **접두가 없는 경로는 파일시스템으로 봐야 합니다.** 그냥 두면 Spring이
`D:/dev/rag-docs`를 classpath로 해석해 기존 설정이 조용히 깨집니다. 윈도 경로는 `D:`처럼 콜론이
들어 있어 "콜론이 있으면 접두"라는 판단도 쓸 수 없었습니다.

옮겨도 **재적재는 일어나지 않습니다.** `ingested_file.file_hash`가 파일 내용의 SHA-256이라
위치가 바뀌어도 값이 같기 때문입니다. 실제로 54개 전부 SKIPPED였습니다.

### 비밀값을 넣는 길

`.env`는 Git에 올리지 않습니다. 그런데 그걸 앱에 먹이는 장치가 없었습니다. 플러그인도
라이브러리도 없이 한 줄로 끝났습니다.

```yaml
spring:
  config:
    import: optional:file:./.env[.properties]
```

`.env`의 `KEY=값` 형식이 `.properties`와 같아서 `[.properties]`만 붙이면 Spring Boot가 그대로
읽습니다. **OS 환경변수가 이 파일보다 우선**하므로 호스팅에서는 대시보드 값이 덮습니다.
로컬은 `.env`, 배포는 환경변수로 **설정 파일 하나가 양쪽에서 돕니다.**

### 실제 키로 붙여 봐야만 걸리는 것들

- **Supabase 직접 연결은 IPv6 전용입니다.** `db.<ref>.supabase.co`에 AAAA 레코드만 있습니다.
  **세션 풀러**(`aws-N-<리전>.pooler.supabase.com:5432`)를 써야 하고, 이때 **사용자명이
  `postgres`가 아니라 `postgres.<project-ref>`로 바뀝니다.** 비밀번호가 맞는데 인증이 실패하면
  거의 이것입니다. 트랜잭션 풀러(6543)는 prepared statement를 못 써서 Hikari에 맞지 않습니다.
- **Cloudflare API 토큰은 `Workers AI - Read`만으로는 추론이 안 됩니다.** 추론이 POST라
  `Edit`까지 필요합니다. 그리고 **계정 이메일 인증 전에는 토큰 생성 자체가 막히는데**, 화면에는
  "An unknown error occurred"만 크게 뜨고 진짜 사유는 그 아래 작게 적힙니다.
- **추론형 모델은 답변이 통째로 빕니다.** 후보로 본 모델 몇이 `max_tokens` 400을 전부 내부
  사고에 쓰고 `content: null`, `finish_reason: length`로 왔습니다. **모델을 고를 때 추론형인지
  먼저 봅니다.**

### Cloudflare 임베딩은 Spring AI로 못 받는다

이것 하나 때문에 클래스를 하나 추가했습니다. curl로는 멀쩡한데 앱에서만 500이 났습니다.

```
com.openai.errors.OpenAIInvalidDataException: `usage` is not set
```

Spring AI 2.0은 공식 OpenAI Java SDK를 쓰고, 그 SDK는 응답의 `usage`를 필수로 봅니다.
**Cloudflare 임베딩 응답의 최상위 키는 `object`·`data`·`model` 셋뿐입니다.** 채팅 응답에는
있어서 채팅은 멀쩡했고 임베딩만 터졌습니다. `CloudflareEmbeddingModel`(106행)을 만들어
`EmbeddingModel`을 직접 구현했습니다. **이 "응답 규격이 조금 다르다" 계열의 문제는 8절에서 한
번 더 나옵니다.**

## 3. 무료로 되는 길부터 찾기

유료 플랜은 쓰지 않는 것이 이 프로젝트의 제약입니다. 호스팅도 **무료 한도를 공식 문서에서
확인하고 숫자로 따져** 골랐습니다.

| 후보 | 결과 | 이유 |
| --- | --- | --- |
| **Render** | **선택** | 0.1 CPU / 512MB, 워크스페이스당 월 750 인스턴스 시간, 카드 없이 가입됨 |
| Google Cloud Run | 보류 | 월 200만 요청 / 180,000 vCPU-초로 넉넉하지만 **결제 계정(카드) 필수** |
| Azure Container Apps | 보류 | Cloud Run과 같은 모양, 역시 카드 필수 |
| Oracle Cloud | 보류 | 상시 가동이지만 카드 필요 + 2026-06에 ARM 한도가 절반(2 OCPU/12GB)으로 축소 |
| Hugging Face Spaces | 탈락 | 공식 문서가 *"Docker Spaces … require a paid plan to create"* |
| Koyeb | 탈락 | 2026-02-17 인수 이후 **신규 가입자에게 무료 티어 미제공** |
| Fly.io | 탈락 | 2024-10-07부로 신규 계정 무료 할당 폐지 |
| Azure App Service F1 | 탈락 | 하루 CPU 60분 — JVM 상시 서비스에 맞지 않음 |

Render의 제약 두 가지는 처음부터 알고 들어갔습니다. **Java가 네이티브 런타임이 아니고**
(Node·Python·Go·Rust·Elixir·PHP·Ruby뿐) **15분간 요청이 없으면 인스턴스가 정지**합니다.

## 4. 0.1 CPU에서 JVM이 뜨긴 하는가

이것이 가장 큰 미지수였습니다. 로컬에서 5.8초에 뜨는 앱이 10분의 1 코어에서 어떻게 될지 알 수
없었습니다. **올려 보기 전에 같은 제약을 로컬에서 흉내 냈습니다.**

```bash
docker run --memory 512m --cpus 0.1 -p 18080:8080 --env-file .env -e PORT=8080 rag-prod:test
```

| 항목 | 0.1 CPU / 512MB 로컬 컨테이너 | Render 실제 |
| --- | --- | --- |
| 기동 | **118.7초** | **51.4초** |
| 메모리 | 기동 후 200MB → 검색 후 246MB / 512MB | — |
| 첫 검색 | 33초 (JIT·커넥션·TLS가 전부 처음) | — |
| 따뜻해진 뒤 검색 | **739 / 739 / 771ms** | 0.42초 (`/api/ingested`) |

**느린 것은 콜드스타트뿐이고 512MB는 넉넉했습니다.** 무거운 일(임베딩·추론·벡터검색)을 전부
남이 하기 때문에, 이 앱이 CPU를 쓰는 구간은 사실상 기동뿐입니다.

JVM 옵션은 이 숫자에 맞춰 골랐습니다 — 힙은 컨테이너 메모리의 70%(`MaxRAMPercentage=70`),
코어가 사실상 하나라 `UseSerialGC`, 기동을 빠르게 하려고 `TieredStopAtLevel=1`입니다.

### Dockerfile과 render.yaml

빌드와 실행을 나눠 `temurin:25-jdk`에서 `bootJar`를 만들고 `25-jre`로 띄웁니다. 테스트는 DB와
Ollama가 필요하므로 이미지 빌드에서 뺐습니다. 최종 이미지 803MB, 실행 jar 166MB입니다(Tika가
큽니다).

포트는 호스팅이 `PORT`로 알려 줍니다(Render는 10000). `server.port: ${PORT:8080}` 한 줄로
받으면 로컬은 8080 그대로입니다. 기동 로그의 `Tomcat started on port 10000`이 그 증거입니다.

서비스 구성은 대시보드에서 손으로 누르지 않고 `render.yaml`(Blueprint)에 뒀습니다. 비밀값
다섯 개만 `sync: false`로 선언해 대시보드에서 받습니다. **대시보드에서 만들면 구성이 저장소에
남지 않습니다.**

### 배포 링크에서 확인한 것

- `/api/ingest` → **54개 전부 SKIPPED**(5초). 해시가 맞아 재적재가 없다는 증거입니다.
- `/api/search` → 1위 **0.6709**(`실행환경_소개_개요.md`). 로컬과 같은 값입니다.
- `/api/ask/stream` → `sources`(+7.5초) → `delta` 9개가 **120~150ms 간격** → `done`(+16.6초).
  걱정하던 **프록시 버퍼링은 없었습니다.**

## 5. Supabase는 7일 쉬면 멈춘다

배포한 뒤 사용자가 일시정지 메일을 받았습니다. 공식 문서가 *"7일간 활동이 적은 프로젝트를
일시정지한다"*, *"하루 몇 건의 DB 요청이면 유지된다"*고 적고 있고, **무료 플랜에서 이 동작을
끄는 방법은 없습니다.**

여기서 Render의 15분 정지와 맞물립니다. **아무도 안 들어오면 앱이 자고 → DB에 요청이 가지
않고 → 7일 뒤 프로젝트가 멈추고 → 데모 링크가 죽습니다.** 둘을 한 번에 막는 것이 keep-alive
크론입니다(cron-job.org 무료).

```
GET https://rag-zxay.onrender.com/api/ingested
0,10,20,30,40,50 9-23 * * *   (Asia/Seoul)
```

고른 이유가 각각 있습니다.

- **왜 `/api/ingested`인가** — GET 한 번으로 DB를 읽어 Supabase 활동으로 잡히면서 **Cloudflare
  뉴런은 쓰지 않습니다.** `/api/search`는 질문을 임베딩하느라 호출이 붙습니다. 응답도
  200/8.3KB/0.42초로 가볍습니다.
- **왜 09~23시인가** — 24시간 깨워 두면 31일에 744시간이라 **월 750시간 한도에 6시간밖에 안
  남습니다.** 재배포 한 번이면 넘깁니다. 15시간 × 31일 = 약 465시간이면 안전하고, 그 시간대에는
  콜드스타트도 사라집니다.
- **첫 핑은 실패로 찍힐 수 있습니다.** cron-job.org는 응답을 30초까지만 기다리는데 기동은 51초
  이상 걸립니다. 요청 자체는 도달해 기동을 시작시키므로 10분 뒤 핑부터 200입니다. **하루 첫
  줄만 빨간 것은 정상입니다.**

## 6. 모델 교체 — 무엇이 풀리고 무엇이 깨지는가

배포 프로필의 답변 모델을 `llama-3.3-70b`로 바꿨으니, 3차부터 쌓아 온 12문항을 다시 재야
했습니다. **같은 날 연속으로 네 라운드**를 돌렸습니다(전원·발열 조건까지 같게 — 7차 교훈).

| # | **A** 교체 전<br>exaone3.5:2.4b | **B** 교체 후<br>llama-3.3-70b | **C** B + 인용 강제 | **D** A + 인용 강제 |
| --- | --- | --- | --- | --- |
| 1·4·5·6·9·12 | 3/3 | 3/3 | 3/3 | 3/3 |
| 2 | 3/3 | 3/3 | 3/3 | **2/3** |
| 3 | 3/3 | **0/3** | **0/3** | 3/3 |
| 7 (절차형) | 3/3 | **0/3** | 2/3 | 3/3 |
| 8 (절차형) | 3/3 | **0/3** | 2/3 | 3/3 |
| 10 (전제 틀림) | 0/3 | 0/3 | 0/3 | 0/3 |
| **11 (할루시네이션)** | **0/3** | **3/3** | **3/3** | 0/3 |
| 회차 합계 | 542/358/395초 | 32/21/26초 | 20/25/31초 | 558/368/398초 |

**11번이 드디어 풀렸습니다.** 6·7차에서 3회 전부 존재하지 않는 Quartz API를 지어내던 질문에
`llama-3.3-70b`는 "문서에서 찾을 수 없습니다"라고 답했습니다. 3차부터 열려 있던 §3의 가설
("더 강한 모델이면 풀린다")이 **절반만 맞았습니다** — 10번은 후보 넷이 전부 실패했습니다.
**10번은 모델로 푸는 문제가 아니라고 기록하고 닫았습니다.**

**그리고 공짜가 아니었습니다.** 3·7·8번이 함께 깨졌습니다. 답변 전문을 보니 판정 오류가
아니었습니다.

- **7번**: A는 "프로젝트 생성 → 포털에서 all-in-one 배포파일 다운로드 → 압축 해제"로 처음부터
  안내하는데, B는 **"목록 중 설치할 컴포넌트를 선택하고 Next를 클릭한다"로 절차 중간부터**
  시작합니다. 마법사를 어디서 여는지가 통째로 빠집니다.
- **8번**: all-in-one 설치가 아니라 **Eclipse 플러그인 설치 절차**를 답했습니다.
- **3번**: "Property Source는 즉시 반영되지 않는다"까지는 맞고 "재시작하면 반영된다"는
  메커니즘만 빠진 **부분 정답**입니다. 이것만은 키워드 판정이 야박한 쪽입니다.

### 인용 강제는 모델에 따라 효과가 반대였다

2차에서 뺐던 "문장 끝에 `[1]`을 붙여라" 규칙을 이 라운드에 끼워 넣었습니다(§3①).
**B→C에서 퇴행은 0건이고 7·8번이 0/3 → 2/3으로 올랐습니다.** 이유가 답변에 보입니다.

```
공통컴포넌트 목록 중 설치하고자 하는 컴포넌트를 선택하고 Next를 클릭한다 [1].
공통컴포넌트 생성 마법사를 사용하여 설치한다 [4].
공통컴포넌트 설정 도구를 사용하여 globals.properties 파일의 정보를 변경한다 [7].
```

조각 하나에 머물던 모델이 문장마다 번호를 달게 되자 `[1][4][5][7][8]`로 **흩어서 끌어오고**,
그 과정에서 빠졌던 "생성 마법사" 단계가 들어왔습니다. 반대로 D(exaone + 같은 규칙)는 11번이
0/3 그대로라 **이득이 0**이었고 2번만 흔들렸습니다.

**그래서 결국 끄기로 했습니다.** 측정만 보면 배포 쪽은 켜는 게 맞지만, 이 규칙은 애초에
**사용자가 2차에서 빼 달라고 한 것**이고(화면의 근거 이동 버튼과 역할이 겹칩니다) 다음 절의
버그까지 끌고 왔습니다. `rag.cite-sources` 스위치만 남겨 두었습니다.

## 7. 켜 보고서야 드러난 버그 — 숫자 한 조각

인용 규칙을 켠 배포본에서 질문하니 답변이 중간에서 끊겼습니다.

```
로깅 서비스는 SLF4J를 도입하였고, Log4j 2를 이용하여 Logging을 수행한다 [
`content` is invalid, received 2
```

Cloudflare 스트리밍을 직접 받아 보고 원인을 확인했습니다.

```
"content":""      "content":1       ← 따옴표가 없다
"content":"\n"    "content":"2\n3"
"content":4       "content":"5\n6"
```

**Cloudflare의 OpenAI 호환 스트리밍은 조각이 숫자 하나일 때 `content`를 JSON 숫자로 보냅니다.**
다른 글자가 섞이면(`"j 2"`) 문자열입니다. 공식 OpenAI Java SDK는 문자열만 받으므로 거기서
죽고, 답변은 그 자리에서 잘립니다. 인용 규칙은 `[`·`1`·`]` 같은 숫자만 든 조각을 양산해 이
버그를 **상시화**했을 뿐, 규칙을 꺼도 "4.3.0"이나 번호 목록에서 터질 수 있습니다.

**왜 측정에서 안 걸렸나** — `evalReport`는 `/api/ask`(비스트리밍)로 잽니다. 전문을 한 번에
받으므로 이 버그가 없습니다. 두 라운드 66콜에서 한 번도 안 터졌고, **화면으로 써 보고서야
드러났습니다.**

고치는 길은 둘이었습니다. (가) 실패하면 비스트리밍으로 한 번 더 받기 — 구현은 작지만 터질
때마다 추론을 두 번 태웁니다. (나) 배포 스트리밍만 직접 파싱하기. **(나)를 골랐습니다.**

```java
JsonNode content = objectMapper.readTree(payload)
        .path("choices").path(0).path("delta").path("content");
return content.isMissingNode() || content.isNull() ? null : content.asString();
```

`asString()`이라 숫자 노드도 `"1"`로 받습니다. `CloudflareChatStreamer`(`@Profile("prod")`)가
`RestClient`로 SSE를 읽고, 모델·온도·`max_tokens`는 `spring.ai.openai.chat.options`를 그대로
읽어 비스트리밍 경로와 설정이 어긋나지 않게 했습니다. 비스트리밍과 로컬 Ollama는 그대로
Spring AI가 맡습니다. **임베딩에 이어 두 번째로, Cloudflare의 응답 규격 때문에 클래스를 손으로
붙인 사례입니다.**

검증은 **인용 규칙을 일부러 켜서** 숫자 조각을 강제한 상태로 했습니다. 죽던 질문이
`{"text":"8"}` 조각을 통과시키고 `done`까지 완주했습니다.

두 가지를 덤으로 배웠습니다.

- **Spring Boot 4의 `ObjectMapper`는 Jackson 3(`tools.jackson.databind`)입니다.** Jackson 2
  jar도 함께 들어 있어 `com.fasterxml...`로 써도 **컴파일은 통과하고 기동에서야** "No qualifying
  bean" 으로 터집니다.
- **`spring.http.client.read-timeout: 30s`는 스트리밍 본문을 자르지 않습니다.** 의심스러워서
  타임아웃을 2초로 낮추고 3초짜리 스트림을 돌려 봤더니 멀쩡히 완주했습니다. 이 값은 응답을 받기
  시작할 때까지만 걸립니다. **추정하지 않고 2분 만에 확인할 수 있는 종류였습니다.**

## 8. 배운 점

**분기점이 되는 측정을 가장 먼저 한다.** "제공처가 달라도 같은 `bge-m3`인가"의 답이 아니었다면
819청크 재적재와 임계값 재측정이 따라오면서 계획 전체가 달라졌습니다. 그래서 그걸 제일 먼저
쟀습니다. **싸고 빠른 측정이 계획을 가를 때, 그 측정이 1번입니다.**

**제약이 심한 환경은 흉내 낼 수 있으면 흉내 내 본다.** `docker run --cpus 0.1 --memory 512m`
한 줄로 "뜨긴 하는가"를 올리기 전에 알았습니다. 실제 Render가 그보다 빨랐으니 **보수적인
쪽으로 틀린 것**이고, 그 방향의 오차는 안전합니다.

**측정 경로와 사용 경로가 다르면 버그는 측정에서 안 걸린다.** `evalReport`는 `/api/ask`로
재는데 사용자는 `/api/ask/stream`을 씁니다. 그 틈에서 이번 버그가 66콜을 멀쩡히 통과했습니다.
**자동 측정은 사람이 쓰는 경로를 대체하지 못합니다.**

**좋아진 지표 하나로 변경을 정당화하지 않는다.** 모델 교체는 11번을 풀었지만 3·7·8번을
깼습니다. 표를 하나만 봤으면 "모델 교체 성공"으로 적었을 것입니다. **12문항을 다 재는 이유가
이것입니다.**

**사용자가 빼 달라고 한 것을 측정 숫자로 되돌리지 않는다.** 인용 규칙은 배포 모델에서 분명히
이득이었지만, 그 규칙이 빠진 이유는 품질이 아니라 **화면 설계**였습니다. 되돌리려면 그 사실부터
꺼내 놓고 이야기했어야 했는데 이번에 그러지 못했습니다. **측정은 선택지를 좁히는 도구이지
결정권자가 아닙니다.**

**"무료"는 조건이 붙은 무료다.** Render는 15분이면 자고, Supabase는 7일이면 멈추고,
cron-job.org는 30초만 기다립니다. 셋을 따로 보면 각각 사소한데, 엮이면 **"어느 날 들어가 보니
링크가 죽어 있는"** 하나의 결과로 모입니다. 무료 티어는 한도뿐 아니라 **이런 조건들이 서로
맞물리는지**까지 봐야 합니다.
