# 6차 개선 — SSE 스트리밍 답변

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · [3차 개선](3차_개선.md) · [4차 개선](4차_개선.md) · [5차 개선](5차_개선.md) · **6차 개선** · [7차 개선](7차_개선.md) · [평가 질문](평가_질문.md)

답변 하나에 40~170초가 걸립니다. GPU가 없어서 그 시간을 줄일 방법이 없습니다. 그래서 줄이는
대신 **기다리는 동안 보이게** 했습니다. 서버가 답변을 다 만든 뒤 한 번에 주던 것을, 만들어지는
대로 흘려보내도록 바꿨습니다.

| | 5차까지 | 6차 |
| --- | --- | --- |
| 답변 전달 | 다 만든 뒤 한 번에 | 조각이 생길 때마다 |
| 첫 글자까지 | 40~170초 | **근거 다음 약 1초** |
| 호출 | `/api/search` → `/api/ask` (검색 2회) | `/api/ask/stream` 한 번 (검색 1회) |
| 의존성 | — | **추가 없음** |

## 1. 먼저 고친 것 — 우선순위 기록

구현 전에 `project_status.md`부터 봤는데 **머리말과 바로 아래 절이 서로 다른 말을** 하고
있었습니다.

| 위치 | 하는 말 |
| --- | --- |
| 머리말 "지금 순서" | `11번 할루시네이션 → 스트리밍 → 배포` — 순서가 정해져 있다 |
| 바로 아래 "다음에 할 일" 절 | "①과 §4 중 하나를 골라야 한다… **고르는 것이 다음 작업이다**" |

5차에서 정리한 규칙이 어느 쪽이 맞는지를 정해 줬습니다 — "**결정하면 이 머리말의 '지금
순서'를 고친다.**" 즉 갱신이 안 된 쪽은 머리말입니다. 머리말의 순서는 4차(09-27)에 쓴
것이고, 10-03 정정(①은 새 시도가 아니라 2차 결정을 되돌리는 일)은 절에만 반영됐습니다.

5차에서 진단한 것과 **같은 메커니즘이 방향만 바꿔 한 번 더** 일어난 것입니다. 그때는 근거가
떨어지고 결론만 옮겨졌고, 이번에는 근거 절만 갱신되고 결론 줄이 남았습니다. 한 사실이 두
군데에 적히면 어느 쪽이든 한쪽만 고쳐집니다.

### §4(스트리밍)를 고른 이유

| | §3① 인용 강제 | §4 스트리밍 |
| --- | --- | --- |
| 비용 | 측정 1라운드 35분, 퇴행하면 +1라운드 | 측정 불필요 (검색·프롬프트 불변) |
| 과녁 | 기준선에서 3/3인 1~8번 | 없음 |
| 성공해도 | (A)/(B)를 갈라야 함 | 바로 보임 |

①은 되돌리기라서 기대값이 낮아진 데다, 더 강한 모델이 들어가면 규칙 수 부담이 작아지므로
**모델 교체(§3④)와 묶는 쪽이 쌉니다.** 그래서 순서를 `스트리밍 → 배포(모델 교체 포함) →
그 라운드에서 ①·10번·11번 재측정`으로 바꿨습니다.

## 2. 서버 — `/api/ask/stream`

```java
@GetMapping(value = "/ask/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter askStream(@RequestParam("question") String question) {
```

이벤트는 네 가지입니다.

| 이벤트 | 내용 |
| --- | --- |
| `sources` | 근거 조각 목록. 0건이면 LLM을 부르지 않습니다 |
| `delta` | 답변 조각 하나 |
| `done` | 답변 전문 |
| `fail` | 생성 중 오류 |

### 왜 GET인가

화면이 쓰는 `EventSource`가 **GET만 지원**합니다. 빌드 도구 없는 화면 한 장에서는 이게
가장 단순합니다. 한글 질문은 화면에서 `encodeURIComponent`로 감쌉니다.

### `/api/ask`는 남긴다

측정 보고서가 전부 `/api/ask` 기준입니다. 엔드포인트를 갈아치우면 이전 회차와 비교가
끊깁니다. `evalReport`도 그대로 `/api/ask`를 씁니다.

### 줄바꿈이 SSE 프레임을 깨뜨린다

처음에 조각을 문자열 그대로 보내려다 멈췄습니다. SSE는 `data:` **한 줄**이 한 덩어리이고
빈 줄이 이벤트의 끝입니다. 답변에는 줄바꿈이 있고 목록형 답변에는 많습니다. 그대로 보내면
두 번째 줄부터 형식에 맞지 않아 버려지거나 이벤트가 중간에 끊깁니다.

그래서 **JSON으로 감싸서** 보냅니다. Jackson이 줄바꿈을 `\n`으로 이스케이프하므로 어떤
답변이 와도 한 줄입니다.

```java
public record StreamText(String text) {
}
```

```
event:delta
data:{"text":" 서비스"}
```

덤으로 한글도 안전합니다. `text/event-stream`을 브라우저는 항상 UTF-8로 읽고, Jackson이
UTF-8로 씁니다.

### 끊길 때 생성도 멈춘다

```java
emitter.onCompletion(subscription::dispose);
emitter.onError(error -> subscription.dispose());
emitter.onTimeout(() -> {
    subscription.dispose();
    emitter.complete();
});
```

화면을 닫아도 구독을 끊지 않으면 Ollama는 끝까지 계산합니다. CPU 추론에서는 그게 수십 초
동안 코어를 잡고 있는 것입니다.

### 오류에 `completeWithError`를 쓰지 않는다

```java
error -> {
    log.warn("스트리밍 답변 생성이 실패했습니다: {}", error.toString());
    send(emitter, "fail", new StreamText(messageOf(error)));
    // completeWithError로 끊으면 EventSource가 재연결해 추론을 또 태운다.
    emitter.complete();
}
```

연결이 비정상으로 끊기면 `EventSource`는 **자동으로 재연결**합니다. 오류로 끊으면 화면이
같은 질문을 다시 쏘고 추론을 한 번 더 태웁니다. 그래서 오류도 **정상 종료로 알립니다** —
`fail` 이벤트를 보내고 스트림을 깨끗이 닫습니다.

이벤트 이름을 `error`로 하지 않은 이유도 같습니다. SSE에서 `event:error`는 `EventSource`의
연결 오류 핸들러로 들어가 **연결 실패와 생성 실패가 섞입니다.**

## 3. 화면 — `EventSource`

```js
stream = new EventSource("/api/ask/stream?question=" + encodeURIComponent(question));
```

### 함정: 닫지 않으면 다시 쏜다

`EventSource`는 스트림이 끝나면 재연결합니다. **완료 이벤트에서 명시적으로 닫지 않으면**
브라우저가 같은 질문을 다시 보내고 CPU 추론 40~170초를 한 번 더 태웁니다.

```js
function finishAsk() {
    stopTimer();
    closeStream();
    busy = false;
    els.submit.disabled = false;
}
```

`done`·`fail`·연결 오류 **세 경로가 모두** 이 함수로 모이게 했습니다. 한 경로라도 빠지면
그 경로에서만 추론이 두 번 돕니다.

### 조각마다 전체를 다시 그린다

```js
stream.addEventListener("delta", function (event) {
    answer += JSON.parse(event.data).text;
    renderAnswer(answer);
    els.answerBlock.hidden = false;
});
```

조각을 DOM에 덧붙이지 않고 **누적 문자열로 전체를 다시 그립니다.** 초당 3~5토큰이라 다시
그리는 비용이 사실상 없고, 대신 HTML 이스케이프와 `[n]` 링크화가 `renderAnswer` 한 군데에만
남습니다. 덧붙이는 방식이면 이스케이프를 두 군데에서 하게 되고, 그건 XSS가 비집고 들어오는
전형적인 자리입니다.

`done`에서는 서버가 보낸 전문으로 **한 번 더 그립니다.** 이어 붙인 결과와 전문이 어긋날
일이 없게 합니다.

### 검색이 두 번 돌던 것이 사라졌다

예전 화면은 `/api/search`로 근거를 먼저 받아 그리고, 이어서 `/api/ask`를 불렀습니다.
`/api/ask`가 안에서 검색을 다시 하므로 **질문 임베딩과 벡터 검색이 두 번** 돌았습니다.
이제 한 스트림이 `sources`를 먼저 보내고 이어서 답변을 흘리므로 한 번입니다.

쓰지 않게 된 `post()` 헬퍼는 지웠습니다.

## 4. 확인

측정 라운드는 돌리지 않았습니다. 검색과 프롬프트를 건드리지 않았고 `/api/ask`도 그대로라
답변 품질이 달라질 자리가 없습니다. 대신 **동작을 세 가지로 확인**했습니다.

### 조각이 실제로 흘러오는가

8081 포트에 따로 띄워 `curl`로 받았습니다(8080은 켜 둔 채로).

```
21:32:57 event:sources
21:32:58 data:{"text":"Integration"}
21:32:59 data:{"text":" 서비스"}
21:32:59 data:{"text":"의"}
21:33:00 data:{"text":" 목적"}
```

근거가 나온 **다음 1초**에 첫 글자가 나옵니다. 그 뒤로 초당 3~5토큰, 예상대로입니다.

### 재연결하지 않는가

브라우저에서 질문하고 네트워크 요청을 셌습니다. `/api/ask/stream` 요청이 질문당 **정확히
1건**입니다. 답변이 끝난 뒤 추가 요청이 없습니다.

확장 프로그램이 첫 요청의 상태를 503으로 표시했는데, `curl`로 재보니 `status=200
content_type=text/event-stream`이고 서버 로그에도 예외가 없습니다. 화면이 `done`을 받고
연결을 끊는 것을 도구가 그렇게 적은 것이지 서버 쪽 문제가 아닙니다.

### 조각이 0건일 때

"오늘 서울 날씨 어때요?"는 임계값 0.50을 넘는 조각이 없습니다. `sources`가 빈 배열로 오고
**LLM을 부르지 않은 채** `문서에서 찾을 수 없습니다.`가 0초에 표시됩니다. 화면에는
"기준 점수를 넘는 문서 조각이 없습니다"가 함께 나옵니다. 예전 동작 그대로입니다.

## 5. 의존성을 추가하지 않았다

`ChatClient...stream()`이 돌려주는 `Flux`에 필요한 `reactor-core`가 Spring AI를 통해 이미
런타임에 있습니다. `SseEmitter`는 `spring-webmvc`에 있습니다. `build.gradle`은 그대로입니다.

## 6. 배운 점

**기록이 두 군데에 있으면 한 군데만 고쳐진다.** 5차에서 "순위는 머리말에서만 말한다"는
규칙을 세웠는데, 정작 이번에 어긋난 것이 그 머리말과 바로 아래 절이었습니다. 규칙을 세우는
것과 고칠 때 둘을 같이 보는 것은 다른 일입니다. 그래서 이번에는 **절을 고칠 때 머리말을
같이 고친다**를 머리말에 적어 두었습니다.

**프로토콜의 줄 단위를 먼저 본다.** SSE는 줄 단위 형식인데 LLM 답변에는 줄바꿈이 있습니다.
보내는 쪽과 받는 쪽 모두 "한 줄"을 가정하는 자리가 있으면, 본문을 그대로 싣지 말고 한 줄로
접히는 형식(JSON)으로 감쌉니다.

**자동 재연결은 비용이 비대칭이다.** 보통은 재연결이 친절한 기본값이지만, 여기서는 한 번
더 연결되는 것이 CPU 추론 40~170초입니다. 기본값이 싼지 비싼지는 기본값이 아니라 **그 뒤에
뭐가 붙어 있는지**가 정합니다. 그래서 정상·오류·연결끊김 세 경로를 모두 한 곳으로 모아
닫았습니다.

**느려지지 않는 변경에는 측정 라운드를 쓰지 않는다.** 한 라운드가 35분입니다. 검색과
프롬프트를 건드리지 않았다면 답변 품질이 달라질 자리가 없으므로, 그 35분은 ①이나 모델 교체
같은 **실제로 품질이 움직이는 변경**에 씁니다.
