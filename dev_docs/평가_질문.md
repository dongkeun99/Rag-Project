## 재는 방법

- 기준 문서: `D:/dev/rag-docs`의 가이드 54개 (838청크, 2026-09-26 적재).
  실행환경 24개 + 공통컴포넌트·개발환경 30개. 5차까지의 기록은 실행환경 24개(411청크)
  기준이므로 5차 이전과 6차 이후의 점수를 직접 비교하면 안 된다.
- 측정 순서: 먼저 `/api/search`로 **1위 점수 · 정답 조각의 순위**를 보고, 그다음
  `/api/ask`로 **답변 내용 · 응답 시간**을 본다. 검색이 틀렸는지 모델이 틀렸는지
  갈라보려면 이 순서여야 한다.
- 판정은 **3회 중 몇 번 맞았는지**로 적는다. 1회 성공을 해결로 적지 않는다(4차 교훈).
- 유형별로 막아야 하는 것이 다르다. 임계값은 주제가 다른 질문(9번)을, 프롬프트는
  주제는 맞지만 답이 없는 질문(11·12번)과 전제가 틀린 질문(10번)을 막는다.
  7·8번은 문서를 적재하기 전까지 "답이 없는 질문"이었으나 6차부터 내용 질문이 됐다.

## 시간을 읽는 법

**한 번 재서 판정하지 않는다.** 4차에서 5번을 1회 성공으로 해결이라 적었다가 10회를
재보니 9회였다. 그 뒤로 3회 기준으로 적는다.

6번을 같은 조건에서 3회 연속 돌린 결과다(5차).

| 회차 | 답변 길이 | 시간 |
| --- | --- | --- |
| 1 | 52자 | 72초 |
| 2 | 243자 | 37초 |
| 3 | 86자 | **13초** |

답변이 가장 짧은 회차가 가장 느리고, 4.7배 긴 답변이 절반 시간에 끝났다. 답변 길이로
설명되지 않는다. 원인은 Ollama의 프롬프트 캐시로 보인다 — 같은 프롬프트를 연속 호출하면
prefill을 재사용하므로 뒤 회차가 극적으로 빨라진다.

따라서 **회차가 다른 개별 질문의 시간을 비교하면 안 된다.** 3차 6번 31초와 4차 104초의
차이도 캐시 상태로 설명될 수 있다. 개별 질문의 시간은 최소 3회 재서 중간값을 본다.
합계는 편차가 어느 정도 상쇄되지만 그것도 1회 측정임을 기억한다.

`temperature`를 0으로 내려도 재현되지 않는다 — 비결정성은 온도가 아니라 CPU 추론의
계산 경로에서 온다.

### 장비 조건 (시간을 읽을 때의 전제)

- GPU 없음. Intel Iris Xe 내장 그래픽뿐이고 Ollama가 쓰지 못하므로 순수 CPU 추론이다.
- 답변 속도는 초당 3~5토큰. CPU로 2.4B 모델을 돌릴 때의 정상 범위다.
- `ollama ps`가 비어 있으면 유휴 5분이 지나 모델이 내려간 것이다. 다음 질문에서 1.6GB를
  다시 올리므로 그 회차가 느려진다. `OLLAMA_KEEP_ALIVE`를 늘리면 없앨 수 있다.

## 남은 과제


6차 기준으로 다시 정리했다. 위쪽은 새로 생긴 것, 아래쪽은 이어지는 것이다.

- **11번 할루시네이션 (가장 시급)**: 인접 주제 문서가 있으면 "찾을 수 없습니다"를 내지
  않고 그것으로 답을 만든다. 6·7차 모두 0/3이고, 7차에는 존재하지 않는 API까지 지어냈다.
  **임계값으로는 못 푼다는 것이 7차에서 확인됐다** — 근거 조각이 0.513~0.548이라 끊으려면
  0.55 이상이 필요한데 5번의 Table 조각(0.5633)이 같이 날아간다. 프롬프트나 모델 쪽에서
  풀어야 한다. 10번과 달리 이건 실사용에서 위험하다 — 그럴듯한 코드가 나오기 때문이다.
- ~~**임계값 0.40 재조정**~~ → **7차에서 0.50으로 바꿔 해결.** 9번이 0건으로 돌아와
  1초에 끝난다. 3번만 조각이 8→4건으로 줄었으나 답은 3/3 그대로다. 다만 임계값은
  코퍼스에 딸린 값이므로 **문서를 추가할 때마다 무관한 질문을 다시 재야 한다.**
- **2번 레이어 혼동 (7차에서 악화: 1/3)**: Spring Security를 화면처리 레이어 기능으로
  답한다. 원인이 좁혀졌다 — 원문의 "공통기반 레이어는 Spring Security / 화면처리는
  입력값 검증" 두 문장이 **한 조각 안에 같이 있어** 모델이 섞는다. 검색 결과는 0.40과
  0.50에서 동일하므로 임계값과 무관하다. 조각 경계 문제이니 청킹 쪽에서 봐야 한다.
- **10번 전제 교정**: 여전히 0/3. 규칙 위치·조각 순서·모델 교체를 모두 시도해 실패했다
  (2·5차). 모델을 바꿨을 때 개선 여부를 재는 지표로 남긴다.
- **12번 머리말**: "문서에서 찾을 수 없습니다" 앞뒤로 설명이 길게 붙는다. 규칙 수를
  늘렸다 줄이는 동안 변하지 않았으므로 `exaone3.5:2.4b`의 성향이다. 기능상 문제는 없다.
- **개요.md 독점**: 실행환경 질문에서 상위 8건 중 평균 3.4건이 개요.md다. 새 영역
  질문에는 0건이므로, 실행환경 쪽 독점은 실행환경 문서를 더 넣어야 풀린다.
- **이미지 링크 노이즈 (새로 생김)**: 개발환경 설치·구현도구 문서는 스크린샷 위주라
  한 청크의 상당 부분이 `![설명](./images/x.jpg)`로 찬다(파일당 7~21개). 기존 실행환경
  문서는 0~3개라 문제가 없었다. 걷어내면 청크 밀도가 오른다.
- **top-k 8 유지**: 5번의 Table 조각이 문서가 늘어난 뒤에도 7위라 줄일 근거가 없다.
