# 5차 개선 — 평가 측정 자동화와 기록 정합성 점검

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · [3차 개선](3차_개선.md) · [4차 개선](4차_개선.md) · **5차 개선** · [6차 개선](6차_개선.md) · [7차 개선](7차_개선.md) · [평가 질문](평가_질문.md)

4차까지 답변 품질은 고정 질문 12개로 쟀지만, 재는 방법은 **손이었습니다.** curl을 36번
돌리고 결과를 눈으로 읽어 마크다운 표에 옮겨 적었습니다. 이번 단계에서는 그 과정을
`./gradlew evalReport` 한 줄로 바꿨습니다.

자동화를 끝내고 기준선을 재는 과정에서 **기록 자체에 틀린 것이 두 개** 나왔습니다. 하나는
"인용 번호 기능이 한 번도 작동한 적이 없다"는 서술이고, 하나는 `project_status.md`에
우선순위 1위 주장이 둘 있다는 것입니다. 둘 다 같은 원인에서 나왔고, 그 원인을 찾는 것이
이번 단계의 절반을 차지했습니다.

| | 4차까지 | 5차 |
| --- | --- | --- |
| 측정 방법 | curl 36번 + 손으로 전사 | `./gradlew evalReport` |
| 한 라운드 비용 | 순수 추론 30분 + 전사 시간 | 순수 추론 34분 35초, 전사 없음 |
| 남는 기록 | 요약 표 | 검색 표 · 답변 표 · 임계값 여유 · **답변 전문** |
| 판정 | 전부 사람 | 키워드 1차 판정 + 사람 확정 |
| 질문 세트 | 문서에만 | `dev_docs/평가질문.yml` (기계가 읽는 원본) |
| 의존성 | — | **추가 없음** |

기준선 보고서는 `dev_docs/측정_원자료/측정_20261003_2242_기준선.md`입니다.

## 1. 왜 지금 자동화했나

남은 작업마다 12문항 × 3회를 다시 재야 합니다. 세어 보면 최소 4라운드입니다.

| 남은 작업 | 라운드 | 추가 비용 |
| --- | --- | --- |
| ① 인용 강제 | 1 (퇴행하면 되돌리고 +1) | — |
| 이미지 링크 제거 + 2번 청킹 | 1 | `force=true` 재적재 약 30분 |
| 모델 교체(배포) | 1 | — |
| 문서 추가 | 1 | 무관한 질문 4개 재측정 |

한 라운드의 순수 추론 시간은 7차 실측으로 계산됩니다 — 1회차 878초 + 2회차 497초 +
3회차 420초 = **1,795초(약 30분)**. 거기에 curl을 손으로 돌리고 표에 옮겨 적는 시간이
붙습니다. 4라운드면 그 작업을 네 번 더 해야 하므로, 지금 자동화하면 **바로 다음 실험에서
회수**됩니다. 게다가 손으로 적으면 답변 전문이 남지 않습니다 — 7차에 "없는 API를 지어내는
단계로 갔다"를 알아챈 것은 운이 좋았던 것이고, 요약만 남기면 다음에는 놓칩니다.

## 2. 하네스 구성

```
dev_docs/평가질문.yml                            질문 세트 (12문항 + 무관 질문 4개)
src/test/java/com/example/rag/eval/
  QuestionSet.java                              yml 로더 + 자동 판정
  RagApi.java                                   떠 있는 앱을 때리는 RestClient
  EvalReportTest.java                           측정 + 보고서 생성 (@Tag("eval"))
dev_docs/측정_원자료/측정_<날짜>_<시각>.md         보고서
```

```bash
./gradlew evalReport                          # 12문항 × 3회
./gradlew evalReport -Prounds=1 -Ponly=2,11   # 2·11번만 1회
./gradlew evalReport -Plabel=인용강제          # 보고서 파일명에 꼬리말
```

**의존성을 추가하지 않았습니다.** 필요한 것이 모두 이미 클래스패스에 있었습니다 —
yml 파싱은 `org.yaml:snakeyaml 2.6`(spring-boot-starter에 딸려 옴), HTTP는
`spring-web 7.0.9`의 `RestClient`, 테스트 실행은 `junit-jupiter 6.0.3`입니다.

### 왜 JUnit 테스트인가

보고서 생성기를 테스트로 두는 것이 깔끔하지는 않습니다. 그래도 이쪽을 골랐습니다.

- `src/test/java`가 "제품 jar에 들어가지 않는 코드"의 제자리입니다. 측정 도구를
  `src/main`에 두면 배포물에 섞입니다.
- Gradle의 `Test` 태스크가 테스트 런타임 클래스패스를 알아서 잡아 줍니다.
- `@Tag("eval")`로 `./gradlew test`에서 빼면 일반 테스트는 그대로 빠릅니다.

```gradle
tasks.named('test') {
    useJUnitPlatform {
        // 평가 측정은 떠 있는 앱과 Ollama가 필요하고 수십 분 걸린다. 일반 테스트에서는 뺀다.
        excludeTags 'eval'
    }
}
```

### 스프링 컨텍스트를 띄우지 않는다

`@SpringBootTest`로 앱을 테스트 안에서 띄우는 대신, **이미 떠 있는 앱을 HTTP로 때립니다.**
측정은 사용자가 쓰는 경로와 같아야 합니다. 컨텍스트를 새로 띄우면 DB 설정·포트·프롬프트
캐시 상태가 실제 사용과 달라지고, 그 차이가 시간 측정에 그대로 섞입니다.

덤으로 DB 설정이 필요 없어 테스트가 가벼워집니다. 앱이 꺼져 있으면 무엇을 켜야 하는지
알려주고 끊습니다.

### 자동 판정의 범위

`키워드`가 모두 있고 `금지어`가 없으면 통과 후보로 적습니다. **의미 판정은 하지 않습니다.**

- **금지어로 알려진 실패를 잡습니다.** 2번은 `Spring Security`, 11번은 `JobDetail` ·
  `scheduleJob` · `getSchedulerInstance` · `TriggerUtils`입니다. 11번의 창작 API가
  7차에 사람 눈으로 발견된 것인데, 이제 자동으로 걸립니다.
- **금지어는 맞는 답에도 걸립니다.** 2번이 "공통기반 레이어는 Spring Security"를 대조로
  언급하면 걸립니다. 그래서 실패로 단정하지 않고 "확인 필요"로 표시만 합니다.
- 그래서 **답변 전문을 보고서에 남깁니다.** 표만 보고 판정하지 않고 전문을 읽습니다.

### 30분 무인 실행을 버티게

한 문항이 실패해도 측정을 계속하고 보고서를 씁니다. 처음 구현에서는 마지막 단계(임계값
여유)에서 예외가 나면 앞의 36회 측정이 통째로 날아갔습니다. 30분을 돌린 뒤 빈손으로
끝나는 설계였던 것입니다. 실패는 답변 자리에 그대로 남겨 사람이 보게 합니다.

### 제품 코드를 한 군데 건드렸다

`/api/search`에 `threshold`·`topK` 조회 파라미터를 더했습니다.

```java
@PostMapping("/search")
public List<SourceRef> search(@RequestBody AskRequest request,
                              @RequestParam(name = "threshold", required = false) Double threshold,
                              @RequestParam(name = "topK", required = false) Integer topK) {
```

무관한 질문의 최고 점수는 **임계값 0으로 조회해야** 보입니다. 지금 임계값 0.50에서는
0건이라 점수가 아예 안 나옵니다. yml을 고쳐 재시작하면 측정 중에 설정이 흔들리므로,
조회 시점에만 덮어쓰고 설정값은 건드리지 않습니다. `/api/ask`에는 두지 않았습니다 —
**답변 측정은 사용자가 쓰는 설정과 같은 조건이어야 합니다.**

## 3. 기준선 측정 — 7차와 같은 판정

34분 35초, 12문항 × 3회.

| # | 유형 | 자동 판정 | 사람 판정 | 중간값 |
| --- | --- | --- | --- | --- |
| 1·3·4·5·6·8·9·12 | — | 3/3 ✅ | 3/3 | 1~114초 |
| 2 | 단일 조각 | 1/3 ⚠ | **1/3 실패** | 14초 |

**✅ 9개, △ 1개(2번), ❌ 2개(10·11번)** — 7차 수동 측정과 판정이 같습니다.

2번은 `Spring Security 연계: Jakarta Commons Validator를 기반으로 Spring Security를

### 7번 3회차 — 하네스가 틀렸다

모델은 **all-in-one 배포파일** 경로로 답했습니다.

```
1. 포털에서 "공통컴포넌트 4.3.0 all-in-one 배포파일"을 다운로드
2. 압축 해제 → egovframework-all-in-one 프로젝트에 복사
3. Maven > Update Project → install → run on server
```

이건 `공통컴포넌트_소개_시작하기.md`에 **실제로 있는 절차**입니다. 문서에 설치 경로가 둘인데
(마법사 / all-in-one) 제가 키워드를 "마법사"만 적어서 맞는 답이 실패로 찍혔습니다.
키워드에 택일을 넣어 고쳤습니다.

```yaml
키워드: ["마법사|all-in-one"]
```

**교훈: 자동 판정의 첫 실패는 모델이 아니라 판정 기준 쪽일 수 있다.** 기준을 의심하지 않고
"7번이 퇴행했다"로 적었으면 없는 문제를 쫓게 됩니다.

### 5번 — 파일 단위 순위로는 안 보이는 것

처음 보고서는 `실행환경_공통기반_ID생성.md 4위`로 찍혔습니다. 그런데 기록에 남은 것은
"**Table Id Generation 조각**이 7위"입니다. 하네스가 파일 단위 최고 순위를 재니까, 같은
파일의 다른 조각이 4위에 있으면 그걸 보고합니다. **top-k 8을 유지하는 근거가 정확히 그
7위 조각인데 그게 보이지 않았습니다.**

조각 본문으로 순위를 찾는 항목을 더했습니다.

```yaml
근거조각키워드: ["Table Id Generation"]
```

→ `"Table Id Generation" 조각 7위`. 기록과 일치합니다.

## 4. 하네스가 같은 것을 재는지 — 교차 검증

새 측정 도구를 믿으려면 **손으로 재던 값을 재현하는지**부터 봐야 합니다.

| 값 | 이번 측정 | 기존 기록 |
| --- | --- | --- |
| 1번 1위 점수 | 0.7318 | 6차 0.732 |
| 3번 조각 수 / 1위 | 4건 / 0.6890 | 7차 "8→4건", 0.6890 |
| 5번 1위 | 0.6354 | "답이 있는 질문 1위 최저 0.6354" |
| 5번 Table 조각 순위 | 7위 | "Table Id Generation 7위" |
| 비트코인 최고 / 출처 | 0.4470 / `개발환경_형상관리_형상관리.md` | 4차 0.4470, Subversion License 표 |

다섯 값이 모두 맞았습니다. 4차가 "비트코인↔crypto, 시세↔License"라고 추정한 출처까지
그대로 나왔습니다.

### 재현되지 않은 값 두 개

임계값 여유 네 줄 중 둘은 4자리까지 일치하고 둘은 맞지 않습니다.

| 무관한 질문 | 이번 측정 | 4차 기록 |
| --- | --- | --- |
| 오늘 서울 날씨 어때요? | 0.4001 | 0.4001 ✅ |
| 비트코인 시세가 어떻게 되나요? | 0.4470 | 0.4470 ✅ |
| 김치찌개 맛있게 끓이는 법 | **0.3571** | 0.3708 |
| 손흥민은 어느 팀에서 뛰나요? | **0.3497** | 0.3413 |

`vector_store`가 HNSW 인덱스를 쓰므로 **근사 탐색이 실제 최대값을 놓친 것**이라고
의심했습니다. 무관한 질문은 838청크의 점수가 0.2~0.45의 좁은 띠에 몰려 있어 recall이
나빠지기 쉬운 구간입니다. `topK`를 올리면 pgvector의 `ef_search`가 함께 커지므로
8 → 100 → 400으로 재봤습니다.

| 질문 | topK 8 | topK 100 | topK 400 |
| --- | --- | --- | --- |
| 김치찌개 | 0.35712170 | 0.35712170 | 0.35712170 |
| 손흥민 | 0.34967482 | 0.34967482 | 0.34967482 |
| 날씨 | 0.40006852 | 0.40006852 | 0.40006852 |

소수점까지 같습니다. **가설 기각** — 근사 탐색 탓이 아니고 지금 값이 실제 최대값입니다.
어긋난 방향도 하나는 위, 하나는 아래라 계산식 차이로도 설명되지 않습니다. 4차의 "질문을
직접 임베딩해 기존·신규를 갈라 재본" 보조 측정 쪽 값으로 보이지만 **원인은 확정하지
못했습니다.**

결론에는 영향이 없습니다 — 무관 최고는 0.4470 그대로이고, 임계값 0.50의 여유는
**+0.1354**, 빈 구간의 가운데는 0.5412입니다.

**손으로 전사한 숫자가 재현되지 않는 사례가 자동화의 이유 그 자체입니다.** 이제부터는
보고서가 기준이고, 보고서에는 커밋 해시가 찍혀 어느 코드에서 나온 값인지 되짚을 수 있습니다.

## 5. 기록이 틀렸던 것 ① — 인용 번호

`project_status.md`에 이렇게 적혀 있었습니다.

> 화면에 `[n]` 클릭 이동 기능이 있는데 프롬프트가 인용을 요구하지 않아 **한 번도 작동한
> 적이 없다.**

**틀렸습니다.** 인용 번호 규칙은 2차 개발 중에 프롬프트에 **있었고, 사용자 요청으로
뺐습니다.** 제거 이유가 [2차 개선](2차_개선.md)에 세 곳 기록돼 있습니다.

> **234행**: 인용 번호를 달라는 규칙은 뺐습니다. 화면의 근거 이동 버튼과 역할이 겹치고,
> 규칙이 하나 줄면 작은 모델이 나머지 규칙을 지킬 여력이 늘어납니다.
>
> **304행**: (답변에 `[n]` 표기가 있으면 화면이 여전히 해당 근거로 이동하는 버튼으로
> 바꿔 줍니다.)
>
> **404·410행**: (트러블슈팅 #2 "정답 조각을 받고도 찾을 수 없다고 답함") … 인용 번호를
> 달라는 규칙까지 있어서 지킬 규칙도 많았습니다. … 인용 번호 규칙을 뺐습니다.

커밋으로도 확인됩니다. 제거는 2차 개발 중에 일어나 커밋 `b9f441c`에는 제거된 상태만
남았고, **현재 프롬프트는 그 커밋과 바이트 단위로 같습니다.**

그러니 `[n]`이 0회인 것은 고장이 아니라 **설계대로의 결과**입니다. 화면의 링크화
코드(`index.html:641`)도 죽은 코드가 아니라 "표기가 있으면 버튼으로 바꿔 준다"는 **의도된
대비**입니다.

### ①의 성격이 바뀐다

이 사실이 `project_status.md` §3①의 전제를 바꿉니다.

- ①은 새로 싸게 해볼 아이디어가 아니라 **2차 결정을 되돌리는 일**입니다.
- 위험이 구체적입니다. 2차 트러블슈팅 #2가 "정답 조각을 받고도 '찾을 수 없습니다'라고
  답함"이었고, **규칙 수를 줄인 것이 그 수정의 일부**였습니다. 지금 3/3인 1~8번이 과녁입니다.
- **11번이 좋아져도 두 가지로 갈립니다.** 11번의 정답이 "찾을 수 없습니다"이기 때문입니다.
  - (A) 주장마다 조각을 지목해야 해서 근거 없는 답을 못 만들게 됐다 → 진짜 해결
  - (B) 규칙이 늘어 모델이 다시 "없다"로 기울었다 → 2차 퇴행의 재발, 해결이 아니다
  - 가르는 기준은 **1~8번**입니다. 11번이 좋아지면서 1~8번 중 하나라도 퇴행하면 (B)입니다.

기준선을 먼저 재 둔 것이 여기서 값을 합니다. (A)와 (B)를 가르려면 비교 대상이 있어야 합니다.

## 6. 기록이 틀렸던 것 ② — 우선순위 1위가 둘

`project_status.md` 안에 1위 주장이 둘 있었습니다.

- §4 스트리밍 "**우선순위가 가장 높은 이유**: …"

모든 문서의 문장을 훑어 흐름을 복원했습니다. **두 주장은 원래 충돌하지 않았습니다.**

### 원인은 두 단계로 일어났다

**① 축이 사라진 지점: `10228f6` (09-25 23:57).** 3차 문서의 "앞으로 할 것"은 **범주별**
목록이었습니다 — 기능 / 문서와 측정 / 인프라. 각 범주의 첫 항목이 "그 범주에서 가장 효과가
큰 것"이었습니다. 이걸 `project_status.md`의 **번호 목록**으로 평탄화하면서 범주가 사라졌고,
"기능 범주에서 체감 개선이 가장 크다"가 "**우선순위가 가장 높다**"로 승격됐습니다.
**3차 원문은 끝까지 "체감 개선이 가장 크다"였고 "우선순위"라는 단어를 쓴 적이 없습니다.**
전역 순위 주장은 옮기는 과정에서 새로 생긴 것입니다.

**② 모순이 드러난 지점: 4차 (09-27).** 11번이 발견되자 §3을 앞에 끼우고 Todo 머리말의
전역 순서를 "11번 → 스트리밍 → 배포"로 다시 썼습니다. 그런데 **이전 1위였던 §4의 근거
문장을 지우지 않았습니다.**

②가 눈에 띄지 않은 이유는 구조에 있습니다. 절 번호가 **순위가 아니라 작성 순서에**
가까웠습니다 — 완료된 §5가 미완인 §4 뒤에 있고 §1·§2도 완료입니다. 동시에 그 번호가
본문에서 **식별자**로도 쓰입니다("배포 작업(7번)과 묶으면", "10번(전제 교정)보다 위험하다").
한 목록이 **순위·식별자·작성 이력** 세 가지를 겸하고 있어서, 순위를 갈아끼울 때 어느 문장을
함께 고쳐야 하는지가 드러나지 않았습니다.

### 같은 패턴이 두 번 일어났다

5절과 6절은 **같은 메커니즘**입니다.

| | 결론만 옮겨진 것 | 탈락한 맥락 | 어디에 남아 있었나 |
| --- | --- | --- | --- |
| 인용 번호 | "`[n]`이 안 나온다" | "2차에서 일부러 뺐다" | `2차_개선.md` |
| 스트리밍 | "가장 ~하다" | "어느 축에서" | `3차_개선.md` |

**통합·요약 단계에서 판단의 근거(축·이유)가 탈락하고 결론만 옮겨집니다.** 결론은 짧고
근거는 길기 때문에, 문서를 모을 때 자연스럽게 근거가 먼저 떨어집니다. 그리고 근거를 잃은
결론은 다음 단계에서 재해석되며 원문보다 강해집니다 — "체감 개선이 가장 크다"가 "우선순위가
가장 높다"로, "프롬프트가 요구하지 않는다"가 "한 번도 작동한 적이 없다"로.

## 7. 문서 구조 수정

`project_status.md`를 이렇게 고쳤습니다.

1. **순위는 Todo 머리말에서만 말한다.** 각 절은 "왜 필요한가"만 적고 순위를 주장하지 않는다.
   §3의 "— 최우선 (다음 작업)"을 지웠다.
2. **§4의 문장에 축을 밝혔다.** "우선순위가 가장 높은 이유" →
   "**속도·체감 축에서는 이것이 유일한 해법이다**(GPU가 없어 실제 시간은 줄일 수 없다).
   다른 축의 항목과 순위를 견준 말이 아니다." **사실은 보존하고 전역 순위 주장만 뺐다.**
3. **번호는 식별자로만 쓴다.** 본문 참조가 있으니 번호는 바꾸지 않고, "번호도 위치도 순위가
   아니다"를 머리말에 적었다. 완료된 절은 `— 완료`를 달아 기록용임을 밝혔다.
4. **머리말에 축을 표로 적었다.** 답변 품질(§3) / 속도·체감(§4) / 완성도(§7) 세 축이고,
   "축이 다른 항목의 '가장 ~하다'는 서로 비교한 값이 아니다"를 명시했다.

이렇게 두면 다음에 새 작업이 끼어들어도 고칠 곳이 **머리말 한 군데**로 줍니다.

`4차_개선.md` §5의 "인용 번호가 나오지 않음" 항목에는 원문을 남기고 `> 2026-10-03 보탬`
인용 블록으로 정정을 덧붙였습니다. 과거 기록을 덮어쓰지 않고 정정을 쌓는 쪽을 골랐습니다 —
무엇을 잘못 알고 있었는지도 기록의 일부입니다.

## 8. 배운 점

**측정을 자동화하면 측정 도구 자체가 검증 대상이 된다.** 첫 보고서에서 7번이 2/3로 찍혔는데
모델이 아니라 제 키워드가 틀렸고, 5번은 파일 단위 순위를 재서 정작 중요한 조각 순위를
놓쳤습니다. 손으로 재던 값 다섯 개를 재현해 보고 나서야 도구를 믿을 수 있었습니다.
**새 측정 도구는 기존 값을 재현하는지부터 본다.**

**가설은 재서 버린다.** 재현되지 않은 점수 두 개를 보고 "HNSW 근사 탐색이 최대값을
놓쳤다"는 그럴듯한 설명을 세웠습니다. `topK`를 8·100·400으로 재보니 소수점까지 같아
기각됐습니다. 2분이면 되는 확인이었고, 안 했으면 틀린 설명을 문서에 남겼을 것입니다.
원인을 끝까지 못 찾은 것은 **"원인 미확정"으로 적습니다.**

**요약은 근거를 떨어뜨린다.** 문서를 모으고 줄일 때마다 결론은 살고 근거는 떨어집니다.
그리고 근거를 잃은 결론은 다음 단계에서 원문보다 강해집니다. 이번에 두 건 모두 그랬습니다.
**"가장 ~하다"를 쓸 때는 어느 축에서인지 함께 적습니다.** 축이 없으면 다음 사람이
전역 순위로 읽습니다.

**30분짜리 작업은 중간 실패를 전제로 짠다.** 측정 하네스의 첫 구현은 마지막 단계에서
예외가 나면 앞의 36회를 통째로 잃었습니다. 긴 작업에서는 "끝까지 성공"이 아니라 "어디서
끊겨도 쓸 것이 남는다"가 기준입니다.

**자동 판정과 의미 판정을 섞지 않는다.** 키워드는 알려진 실패를 싸게 잡지만 맞는 답도
걸립니다. 판정을 자동화하는 대신 **표시만 하고 답변 전문을 남겨** 사람이 읽게 했습니다.
