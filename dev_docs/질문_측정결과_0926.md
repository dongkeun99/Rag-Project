### 11번 — 이번 측정의 가장 큰 발견 (할루시네이션)

"배치처리 레이어에서 Job Launcher는 어떻게 설정하나요?"에 **"찾을 수 없습니다"가 아니라
그럴듯한 오답을 3회 모두 지어냈다.**

```java
JobDetail jobDetail = new JobDetail("myJob", sched.DEFAULT_GROUP, DumbJob.class);
Trigger trigger = TriggerUtils.makeDailyTrigger(8, 30);
sched.scheduleJob(jobDetail, trigger);
```

이건 `실행환경_공통기반_스케줄링.md`의 **Quartz** 코드다. Spring Batch의 `JobLauncher`와
Quartz의 `Scheduler`는 다른 것인데 모델이 둘을 섞었다. 검색 결과를 보면 이유가 보인다 —
2~7위가 전부 스케줄링 문서이고 점수가 0.513~0.548로 임계값을 넉넉히 넘는다. **주제가
인접한 문서가 있으면 모델은 "없다"고 하지 않고 그것으로 답을 만든다.**

7·8번은 이 실패를 잡지 못했다. 그 두 질문은 해당 주제 문서가 **아예 없어서** 조각이
약했고, 그래서 모델이 포기했다. 11번은 인접 문서가 **있는** 경우다. 새 질문이 기존
질문보다 어렵고 현실적이다 — 실사용에서 위험한 쪽은 이쪽이다.

12번이 통과한 것과 대비된다. 12번(지식관리 지식맵)은 상위 조각이 공통컴포넌트 설치·생성
이야기라 질문과 결이 달라 모델이 답을 만들지 못했다.

### 9번 — 임계값 0.40이 무관한 질문을 더는 못 막는다

0건이어서 LLM을 타지 않는 것이 이 질문의 존재 이유였는데, **0.4001로 임계값을 0.0001
차이로 넘겨 1건이 잡힌다.** 답 자체는 프롬프트가 막아 3회 모두 맞았다.

잡힌 조각은 `공통컴포넌트_보안_로그인세션관리.md`의 쿠키 표다. "서버의 최근 시간 /
시스템의 최근 시간 / 만료 시간 / Epoch시간"으로 시간 이야기뿐이고, 질문의 "오늘"이
거기 걸렸다.

질문을 직접 임베딩해 기존·신규 문서를 갈라 재봤다.

| 무관한 질문 | 기존 24개(411청크) 최고 | 새 30개(427청크) 최고 |

**네 질문 모두 새 문서 쪽이 높다. 우연이 아니다.** 기존 실행환경 문서는 AOP·IoC·MyBatis
같은 프레임워크 내부 용어라 일상 언어와 멀었다. 새로 넣은 공통컴포넌트·개발환경 문서는
로그인·시간·게시판·회원·설치·다운로드·라이선스·암복호화처럼 **일상 어휘에 닿는다.**
비트코인 0.447이 걸린 곳이 `공통컴포넌트_보안_암복호화.md`의 "crypto ARIA 암복호화
라이브러리"와 `개발환경_형상관리_형상관리.md`의 "Subversion License" 표인 것이 그 증거다
(비트코인↔crypto, 시세↔License).

**교훈: 임계값은 코퍼스와 무관한 값이 아니다.** 0.40은 어휘가 좁은 411청크에서 잰 값이고,
문서 범위를 넓히면 무관한 질문의 최고 점수가 따라 올라가 여유가 사라진다. 이번에 여유가
+0.02에서 -0.0001로 줄었다. **문서를 추가할 때마다 무관한 질문을 다시 재야 한다.**

측정된 빈 구간은 **0.447(무관 최고) ~ 0.594(관련 질문 1위 최저)** 이고, "가운데, 애매하면
낮게" 원칙대로면 **0.50**이 후보다. 아직 적용하지 않았다.

### 9번 — 목적 달성

**1초 × 3회.** 0건이라 LLM을 아예 타지 않는다. 6차에는 조각 1건이 잡혀 2/8/2초가
걸렸다. 답은 6차에도 맞았지만 "임계값이 막는다"는 이 질문의 존재 이유가 돌아왔다.
무관한 질문을 임계값에서 끊으면 수십 초가 아니라 1초에 끝난다.

### 3번 — 조각이 절반으로 줄었는데 퇴행 없음

8건 → 4건으로 5~8위(0.500~0.482)가 잘렸는데 3회 모두 정확하다. 오히려 답이 더
깔끔해졌다. **답이 1위 조각(0.689)에 있으면 하위 조각은 기여하지 않는다**는 것을
보여준다. 임계값을 올리는 비용이 걱정했던 것보다 작다.

### 2번 — 퇴행했지만 임계값 탓이 아니다

3회 중 2회가 Spring Security를 화면처리 레이어 기능으로 답했다(6차는 1회). 원문은
이렇게 구분한다.

> 인증, 권한 같은 일반적인 개념의 Security 서비스는 Spring Security를 활용한 **공통기반
> 레이어**에서 제공한다. **화면 처리 레이어**의 Security 서비스는 입력값 유효성 검증
> 기능을 제공한다.

두 문장이 **한 조각 안에 같이 들어 있어** 모델이 둘을 섞는다. 2번의 검색 결과는
0.40과 0.50에서 완전히 같으므로 임계값이 원인일 수 없다. 표본 3회에서 1/3과 2/3은
편차 범위이기도 하다. 원인은 조각 경계이지 임계값이 아니다.

### 11번 — 할루시네이션이 오히려 나빠졌다

3회 모두 실패는 같지만 내용이 달라졌다. 6차에는 문서에 있는 **진짜 Quartz 코드**를
가져다 잘못 적용했다. 7차에는 존재하지 않는 API를 지어낸다.

```java
JobLauncher jobLauncher = schedulerFactory.getSchedulerInstance();
jobLauncher.run(jobDetail);
```

`schedulerFactory.getSchedulerInstance()`도 `jobLauncher.run(jobDetail)`도 Quartz에도
Spring Batch에도 없다. 문서에서 베끼는 단계를 넘어 **API를 창작하는 단계**로 갔다.
임계값을 올려 조각 수가 줄어든 것이 오히려 근거를 성기게 만든 것으로 보이나, 3회
측정이라 확정하지 못한다.

### 결론

**임계값 0.50을 채택한다.** 얻은 것은 9번의 성질 복구(무관한 질문을 1초에 끊음)이고,
잃은 것은 없다. 3번이 유일하게 조각을 잃었지만 답은 그대로다.

시간은 비교하지 않는다. 6차 1회차 합계 900초, 7차 878초로 차이가 없고, 개별 질문의
시간은 프롬프트 캐시 상태에 좌우되므로 회차가 다른 값을 비교하면 안 된다(5차 교훈).

**임계값으로 풀리지 않는 것이 분명해졌다.** 10번(전제 교정)과 11번(할루시네이션)은
검색이 아니라 생성 쪽 문제다. 11번은 근거 조각이 0.513~0.548로 임계값을 넉넉히 넘기
때문에, 이걸 끊으려면 임계값을 0.55 이상으로 올려야 하는데 그러면 관련 질문의 근거도
같이 날아간다(5번의 Table 조각이 0.5633). 프롬프트나 모델 쪽에서 풀어야 한다.
