# 7차 개선 — 답변이 느린 이유를 쪼개 보고, 조각의 군더더기를 걷어냄

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · [3차 개선](3차_개선.md) · [4차 개선](4차_개선.md) · [5차 개선](5차_개선.md) · [6차 개선](6차_개선.md) · **7차 개선** · [평가 질문](평가_질문.md)

6차에서 스트리밍을 붙이고 나니 **시간이 어디로 가는지가 눈에 보이기 시작했습니다.** 첫 글자가
뜨기까지 80초가 걸리고, 거기서부터 40초 동안 글자가 흘렀습니다. 지금까지 "답변에 40~170초"
한 줄로 적어 두었던 것을 이번에 **단계별로 쪼개 쟀습니다.**

결론부터 — **느린 곳은 생성이 아니라 프롬프트를 읽는 단계(prefill)였습니다.** 그리고 그
단계는 토큰 수에 정비례하므로, 조각에 섞여 있던 마크다운 이미지 링크를 걷어내는 것이
품질을 건드리지 않고 시간을 줄이는 유일한 수단이었습니다.

| | 6차까지 | 7차 |
| --- | --- | --- |
| 느린 이유 | "GPU가 없어서" | prefill 1,400~1,750토큰 × 약 45 tok/s |
| 조각 속 이미지 링크 | 그대로 (12문항 본문의 10.4%) | 적재 단계에서 제거 |
| 모달에 보이던 `!`·`10.` | 조각이 링크·번호 한가운데에서 잘림 | 둘 다 사라짐 (819청크 전체 0건) |
| 답변 길이 상한 | `num-predict: 300` | **400** (조각 밀도가 올라 절차형 답변이 끊겼다) |
| 전원 | 배터리/AC 구분 없음 | 측정 시 AC 권장(근거 있음) |

## 1. 어디서 시간이 가는가

Ollama가 응답에 실어 주는 `prompt_eval_duration`·`eval_duration`을 그대로 읽었습니다.
앱이 쓰는 것과 같은 프롬프트·같은 옵션으로 때렸습니다.

| 단계 | 모델이 올라가 있을 때 | 5분 유휴 뒤 첫 질문 |
| --- | --- | --- |
| 검색 (bge-m3 임베딩 + 벡터) | 0.2~0.5초 | 3.1~4.8초 |
| 모델 적재 | 0초 | 3.1~4.9초 |
| **프롬프트 평가(prefill)** | **26~38초** (1,330~1,749토큰, 45~51 tok/s) | 같음 |
| 생성(decode) | 13~41초 (93~190토큰, 4.6~7.1 tok/s) | 같음 |

**첫 글자까지의 시간은 거의 전부 prefill입니다.** 모델이 문서 조각 8개를 "읽는" 시간이고,
첫 글자가 나오기 전에 끝나야 하는 일이라 스트리밍으로 숨길 수 없습니다.

실제 사용자가 "게시판 설치" 질문에서 본 숫자와도 맞습니다.

```
공통컴포넌트 중 게시판 컴포넌트는 어떻게 설치하나요?   (AC, 모델 올라간 상태)
  prefill  38.3초  (1,749토큰, 45.7 tok/s)   ← 첫 글자까지
  decode   40.9초  (190토큰, 4.6 tok/s)      ← 스트리밍으로 보이는 구간
  합계     79.3초
```

화면에서 잰 값은 첫 글자 40초, 완료 77초였습니다.

### 장비는 범인이 아니다

| 의심 | 측정 | 판정 |
| --- | --- | --- |
| 노트북이 오래돼서 | i5-1240P(12코어/16스레드, 2022), NVMe SSD 2장, 모델 적재 3.1초 | **아니다** |
| 다른 앱을 많이 띄워서 | 측정 중 CPU 유휴 18%, 여유 RAM 3.9GB | **평소엔 아니다**. 앱 재시작 직후 첫 질문만 예외 |
| CPU 한계라서 | prefill 45 tok/s, decode 5 tok/s | **맞다. 단 "CPU가 느려서"가 아니라 GPU를 못 써서** |

Ollama가 인텔 내장 GPU를 쓰지 못해 전부 CPU로 돕니다. `num_thread`를 12·8·6·4로 바꿔
봤지만 전부 기본값보다 느려서 건드릴 이유가 없었습니다.

### 전원 — 어댑터는 10~15%

같은 질문·같은 상태로 짝지어 쟀습니다.

| 단계 | 배터리 | AC | 차이 |
| --- | --- | --- | --- |
| 검색 (cold) | 4.8초 | 3.1초 | −35% |
| 모델 적재 (cold) | 4.9초 | 3.1초 | −37% |
| prefill (질문 6, warm) | 29.1초 / 45.7 tok/s | 26.1초 / 51.0 tok/s | −10% |
| decode (질문 6, 93~94토큰) | 17.2초 / 5.5 tok/s | 13.1초 / 7.1 tok/s | −24% |
| **합계** | **46.4초** | **39.3초** | **−15%** |

재현되는 차이지만 판을 뒤집지는 않습니다. **평소 질문에는 굳이 꽂을 필요 없고,
`evalReport`처럼 30분 연속으로 도는 측정에서는 꽂아 둡니다** — 속도 때문이라기보다
측정 조건을 고정하기 위해서입니다.

### 연속으로 쓰면 느려진다

prefill 속도가 **쉰 상태 45~51 tok/s → 10분 넘게 연속 추론한 뒤 23~27 tok/s**로 떨어졌고,
몇 분 쉬니 46 tok/s로 돌아왔습니다. 발열입니다.

기준선 측정의 회차별 합계가 1,151 → 396 → 514초로 3회차가 2회차보다 느렸는데, 지금까지
프롬프트 캐시로만 설명하던 자리에 **설명이 하나 더 생겼습니다.** 1회차→2회차의 큰 단축은
캐시가, 2회차→3회차의 되돌아감은 발열이 설명합니다.

## 2. 이미지 링크 — 쟤가 토큰을 먹고 있었다

"게시판 설치" 질문의 조각 8건을 뜯어보니 이랬습니다.

```
[1] 개발환경_구현도구_공통컴포넌트마법사.md | 495자 | 이미지링크 3개 146자 | 끝이 잘림 "…DB를 선택해야 한다.\n\n   !"
[4] 공통컴포넌트_소개_시작하기.md          | 470자 | 이미지링크 3개 131자 | 끝이 잘림 "…en-update.jpg)\n\n7."
[5] 개발환경_구현도구_공통컴포넌트마법사.md | 557자 | 이미지링크 4개 208자 | 끝이 잘림 "…열고 다운로드 받는다.\n\n   !"

합계 3,281자 중 이미지 링크 898자 (27.4%), 끝이 잘린 조각 3/8건
```

화면의 근거 모달에 `!` 한 글자나 `7.`만 덩그러니 보이던 것이 이것이었습니다.
`![대상 프로젝트 선택](./images/commngt-select-project.png)` 한가운데에서 250토큰 경계가
떨어지면 `!`만 남고, 목록 번호 뒤에서 떨어지면 `7.`만 남습니다. **버그가 아니라 청킹 경계
효과**였지만, 어느 쪽이든 조각에 정보는 없고 토큰만 있습니다.

그림 파일 자체는 적재하지 않으므로 이 링크는 **모델에게 아무것도 알려주지 못합니다.**

### alt 텍스트도 같이 지운 이유

문서 폴더 전체에 이미지 링크가 191개 있고, 그중 **37개가 `![image]`** 입니다. 나머지도
`![Run on Server]`, `![Maven Install]`처럼 바로 앞 절차 문장과 겹치는 UI 라벨입니다.
남겨 둘 값이 없다고 보고 링크 전체를 지웠습니다.

### 구현

`IngestService`가 파일을 읽은 직후, 제목으로 절을 나누기 **전에** 걷어냅니다. 적재 단계에서
지우므로 조각이 링크 한가운데에서 잘릴 일 자체가 없어집니다.

```java
String text = stripImageLinks(raw.getText());
```

```java
private String stripImageLinks(String text) {
    if (text == null) {
        return null;
    }
    String stripped = IMAGE_LINK.matcher(text).replaceAll("");
    stripped = BLANK_LINE.matcher(stripped).replaceAll("");
    return MULTI_NEWLINE.matcher(stripped).replaceAll("\n\n");
}
```

이미지만 있던 줄은 공백만 남으므로 줄째로 지우고, 빈 줄이 겹치면 하나로 줄입니다.
본문 링크(`[Data Source Explorer](./dbio-editor-data-source-explorer.md)`)는 건드리지
않습니다 — 느낌표가 앞에 붙은 것만 지웁니다.

### 재적재가 필요하다

조각의 내용이 바뀌므로 임베딩을 다시 만들어야 합니다. `/api/ingest?force=true`입니다.
8080에 떠 있는 앱은 예전 코드라 지우지 못하므로, **새 코드를 8081에 따로 띄워 적재**하고
같은 DB를 보는 8080은 그대로 두었습니다.

## 4. 예상이 빗나간 곳 — 프롬프트는 6.5%만 줄었다

재적재 전 A/B에서는 같은 조각에서 링크만 걷어내 **1,749 → 1,388토큰(−20.6%)** 이었습니다.
그런데 실제로 재적재하고 나니 같은 질문이 **1,749 → 1,635토큰(−6.5%)** 이었습니다.

이유는 간단합니다. **청킹이 비워진 자리를 실제 본문으로 다시 채웁니다.** 250토큰이라는
예산은 그대로인데 링크가 빠졌으니, 그 자리에 다음 문장들이 들어옵니다. A/B는 "같은 조각에서
링크만 뺀" 상태를 쟀고, 실제로는 "같은 예산에 내용이 더 들어간" 상태가 됩니다.

그래서 이 변경의 성격이 바뀝니다.

| | A/B가 예상한 것 | 실제로 일어난 것 |
| --- | --- | --- |
| 프롬프트 | −20.6% | −6.5% |
| 성격 | 속도 개선 | **밀도 개선** (같은 8조각에 실제 내용이 더 들어감) |

12문항 전체로 봐도 본문이 31,803 → 29,656자(−6.8%)로, 이미지 링크로 지웠던 3,299자의
**3분의 1만큼만** 줄었습니다. 나머지 3분의 2는 실제 본문으로 바뀐 셈입니다.

**측정 전 A/B는 방향은 맞혔지만 크기는 틀렸습니다.** 적재 파이프라인을 바꾸는 변경은
파이프라인을 실제로 돌려봐야 크기를 알 수 있습니다.

### 10번이 조용히 좋아졌다

"실행환경의 **다섯 가지** 서비스 그룹이 뭔가요?"는 전제가 틀린 질문이고, 기대 답변은
"8개라고 바로잡고 8개를 나열"입니다. 기준선에서는 **3회 모두 5개만** 나열했습니다.

```
기준선 (1·2·3회차 모두)
1. 화면처리  2. UX처리  3. 업무처리  4. 데이터처리  5. 연계통합
```

이번에는 **3회 중 2회가 8개를 전부** 나열했습니다.

```
이번 1·2회차
화면처리, UX처리, 업무처리, 데이터처리, 연계통합, 배치처리, 모바일 서비스, 공통기반
```

"8개입니다"라고 **말하지는 않아** 키워드 판정은 그대로 실패입니다. 그래도 목록을 다섯에서
끊지 않게 됐습니다. 조각의 밀도가 올라가 8개가 한 조각 안에 다 들어온 것으로 보입니다.
**0/3이라는 숫자는 그대로지만 안에서 일어난 일은 달라졌습니다** — 자동 판정만 보면
놓쳤을 변화입니다.

### 7번은 통과했지만 답하는 경로가 바뀌었다

기대 답변은 "공통컴포넌트 생성 마법사로 설치한다"입니다. 기준선은 3회 중 2회가 마법사
경로(`eGovFrame > Implementation > Add eGovFrame Common Component`)로 답했는데, 이번에는
**3회 모두 all-in-one 배포파일 경로**로 답했습니다. 키워드가 `마법사|all-in-one` 택일이라
자동 판정은 통과했고 문서에 있는 절차이므로 틀린 답도 아닙니다. 다만 1순위로 기대하던
경로가 바뀐 것은 기록해 둡니다.

### 새로 생긴 문제 — `num-predict: 300`에 걸린다

답변이 길어지면서 **상한에 걸려 문장 중간에서 끊기는 답변이 생겼습니다.**

```
7번 2회차 … 5. **프로젝트 빌드 및 실행**: Maven clean, Maven install을 실행한 후 …
            6. **설정 파일 변경**: 공통컴        ← 여기서 끝
```

같은 질문의 답변 길이를 재보면 **267~300토큰**으로 상한에 바짝 붙어 있습니다(기준선에서는
190토큰이었습니다). 상한을 800으로 풀고 재보니 296토큰에서 스스로 멈췄습니다 — 즉 지금
필요한 길이가 300 근처라 **운에 따라 잘립니다.**

- 고치는 법: `num-predict: 300` → `400`. 재적재도 재측정도 필요 없고 재시작만 하면 됩니다.
- 비용: 300토큰 안에서 끝나는 답변은 **아무 영향이 없습니다**(상한이지 목표가 아니다).
  300을 넘기려는 답변만 길어지고, 4.3 tok/s이므로 100토큰이면 약 23초입니다.
- 이 프로젝트는 길이와 속도를 맞바꾸는 선택을 계속 해 왔으므로 사람이 정했습니다. **§6에서 400으로 올렸습니다.**

### 시간

| | 기준선 (10-03) | 이번 (10-10) |
| --- | --- | --- |
| 1회차 | 1,151초 | 802초 |
| 2회차 | 396초 | 443초 |
| 3회차 | 514초 | 465초 |
| **합계** | **2,061초** | **1,710초 (−17%)** |

**이 −17%를 이미지 링크 제거의 효과로 읽으면 안 됩니다.** 이번 측정은 AC 전원이었고
기준선의 전원 상태는 기록돼 있지 않습니다. 전원만으로 10~15%가 설명되고, 프롬프트는
6.5%밖에 줄지 않았습니다. **조건이 다른 두 측정의 총 시간을 빼서 효과라고 적지 않습니다.**

## 6. 뒤이어 고친 둘 — 외톨이 번호와 답변 길이 상한

측정이 남긴 두 가지를 바로 정리했습니다. 재적재가 한 번 더 필요했지만(21분) 둘을 묶어
한 번에 끝냈습니다.

### 외톨이 목록 번호

화면의 근거 모달에 `10.` 만 덩그러니 보이던 것입니다. 원본은 멀쩡하고 **250토큰 경계가
번호 바로 뒤에 떨어져서** 생깁니다 — 항목의 본문은 다음 조각으로 가고 번호만 남습니다.

```
… 9. DB의 Connection Test가 정상적으로 종료되면 아래와 같은 메시지 창이 뜬다.

10.                                    ← 여기서 조각이 끝남
```

**이미지 링크와 걷어내는 시점이 다릅니다.** 이미지 링크는 원문에 있는 것이라 파일을 읽은
직후에 지우지만, 외톨이 번호는 **자르는 자리가 만드는 것**이라 조각으로 쪼갠 뒤에 뗍니다.

```java
body = stripTrailingListMarker(body);
```

12문항에서 4건 → **0건**이 됐고, 코퍼스 전체로도 819청크 중 0건입니다. 화면에서 보던
그 조각도 `9. … 메시지 창이 뜬다.` 로 깔끔하게 끝납니다.

### `num-predict: 300` → `400`

| 걱정했던 것 | 실제 |
| --- | --- |
| 컨텍스트 초과 | 최대 프롬프트 약 1,650토큰 + 400 = 2,050. `num-ctx` 4,096에 한참 못 미침 |
| 메모리 | 안 늘어남. KV 캐시는 `num-ctx`로 잡힘 |
| 전체 속도 | 300 안에서 끝나는 답변은 영향 0. **상한이지 목표가 아니다** |
| 오류 | 없음. 가장 긴 프롬프트(11번)로 400을 직접 돌려 확인 |

앱의 `/api/ask`로 7번을 두 번 돌려 **둘 다 끝까지 완결**되는 것을 확인했습니다(721자, 810자).
`6. **설치 확인**: …` 까지 나오고 멈춥니다. 전에는 `6. **설정 파일 변경**: 공통컴` 에서
끊기던 자리입니다.

대신 그만큼 느려집니다 — 160초, 115초. 길어진 답변의 값입니다.

**여유는 고정이 아닙니다.** `top-k`나 `chunk-size`를 올리면 프롬프트가 커져 `num-ctx`까지의
여유가 줄어듭니다. 그때는 `num-predict`도 같이 봐야 합니다. 그래서 `application.yml`의
주석에 계산식을 남겼습니다.

### 두 번째 재적재 뒤 수치

| | 1차 재적재 후 | 2차 재적재 후 |
| --- | --- | --- |
| 청크 | 819 | 819 |
| 이미지 링크 | 0 | 0 |
| 끝이 잘린 조각 (12문항) | 4건 | **0건** |
| 12문항 본문 | 29,656자 | 29,454자 |
| 1위 점수 | — | 7번만 0.7230 → 0.7243, 나머지 동일 |
| `"Table Id Generation"` | 7위 | **7위** |
| 무관 질문 최고 | 0.4470 | 0.4470 |

검색 쪽은 사실상 그대로입니다. 외톨이 번호 4건을 떼는 변화라 그래야 맞습니다.
답변 쪽은 다시 재지 않았습니다 — 조각 내용이 번호 네 개만큼만 달라졌고,
`num-predict`는 상한이라 300 안에서 끝나던 답변을 바꾸지 못합니다.

## 7. 배운 점

**파이프라인을 바꾸는 변경은 파이프라인을 돌려봐야 크기를 안다.** 재적재 전 A/B는
−20.6%를 예상했지만 실제는 −6.5%였습니다. 청킹이 비워진 자리를 본문으로 다시 채우기
때문인데, 이건 A/B 설계상 보이지 않는 자리였습니다. **방향은 A/B로, 크기는 실측으로.**

**지표가 그대로여도 안에서는 바뀔 수 있다.** 10번은 0/3 → 0/3으로 숫자가 똑같지만,
다섯 개만 나열하던 답이 여덟 개를 다 나열하는 답으로 바뀌었습니다. 답변 전문을 보고서에
남기기로 한 5차의 결정이 여기서 값을 했습니다. **표만 봤으면 "변화 없음"으로 적었을
것입니다.**

**한 군데를 늘리면 다른 쪽 상한에 닿는다.** 조각의 밀도를 올렸더니 답변이 길어졌고,
2차에 정해 둔 `num-predict: 300`에 걸렸습니다. 상한은 그걸 정할 당시의 입력 크기를 전제로
한 값이라, 입력을 바꾸면 같이 봐야 합니다.

**조건이 다른 숫자는 빼지 않는다.** 총 시간이 17% 줄었지만 전원 상태가 달라 그대로
효과로 적을 수 없습니다. 5차에서 "회차가 다른 개별 질문의 시간을 비교하면 안 된다"고
적었던 것과 같은 함정이 라운드 단위에서도 있습니다.

**증상이 같아도 만들어진 자리가 다르면 고치는 자리도 다르다.** 모달에 보이던 `!` 와 `10.`
은 화면상 똑같이 "조각 끝에 의미 없는 한 조각"이었지만, 하나는 **원문에 있던 것**이고
하나는 **자르는 자리가 만든 것**이었습니다. 그래서 하나는 파일을 읽은 직후에, 하나는
조각으로 쪼갠 뒤에 걷어냅니다. 둘을 한 자리에서 처리하려 했으면 어느 한쪽은 놓쳤습니다.
