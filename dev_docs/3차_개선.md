# 3차 개선 — 실제 문서 적재 · 제목 기준 청킹 · 평가 질문 10개

> [README](../README.md) · [1차 구현](1차_구현.md) · [2차 개선](2차_개선.md) · **3차 개선**

2차까지는 실습용 샘플 PDF 3개(조각 17개)로 튜닝값을 정했습니다. 표본이 작아 임계값 0.40과 청크 250토큰의 근거가 약했습니다.

3차에서는 실제 전자정부 표준프레임워크 문서를 넣고, 고정 질문 10개로 측정 체계를 만든 뒤, 그 숫자를 근거로 청킹과 검색 설정을 고쳤습니다.

## 한눈에 보기

| 구분 | 2차 | 3차 |
| --- | --- | --- |
| 문서 | 실습용 샘플 PDF 3개 (17청크) | 실행환경 가이드 md 24개 (411청크) |
| 청킹 | 파일 전체를 250토큰으로 기계 분할 | 제목으로 절을 나눈 뒤 250토큰 분할 + 제목 경로 접두 |
| 검색 개수 | top-k 3 | top-k 8 |
| 폴더에서 지운 문서 | DB에 청크가 남음 | 적재할 때 자동 정리 |
| 평가 | 고정 질문 3개, 눈으로 확인 | 고정 질문 10개 + 유형별 판정 ([평가_질문.md](평가_질문.md)) |
| 화면 | 근거 목록·점수 막대·인용 이동 | + 전문 모달, 이전/다음 고정, 답변 시간, 초기화 |
| 통과 | — | 10개 중 9개 |

## 1. 실제 문서로 교체

포털 가이드를 마크다운으로 옮긴 공식 저장소([eGovFramework/egovframe-docs](https://github.com/eGovFramework/egovframe-docs))에서 실행환경 가이드 24개를 받았습니다. PDF 대신 마크다운을 고른 이유는 세 가지입니다.

- `.md`는 이미 지원하는 확장자다
- PDF는 머리말·쪽번호·단 나눔이 텍스트에 섞이는데 마크다운은 깨끗하다
- 파일 단위로 원하는 것만 골라 담을 수 있다

문서를 복사할 때 걸린 함정이 세 가지 있었습니다.

| 함정 | 대응 |
| --- | --- |
| `ingestAll`이 `Files.list`를 쓰므로 하위 폴더를 읽지 않는다 | 문서 폴더 바로 아래에 평평하게 둔다 |
| 저장소에 `_index.md`가 33개 있고, 출처 키가 파일명뿐이라 서로 덮어쓴다 | `실행환경_연계통합_RESTful.md`처럼 경로를 이름에 넣는다 |
| `_index.md`·`intro.md`는 링크 목록만 있어 노이즈가 된다 | 목차 성격 파일은 제외한다 |

그리고 사이트 설정용 YAML frontmatter(`url:`, `menu:`, `weight:`)를 걷어냈습니다. 250토큰 청크에서는 이 값들이 첫 조각의 상당 부분을 차지합니다.

한 가지 중요한 발견이 있었습니다. **샘플 PDF와 실제 문서가 사실이 충돌합니다.** 실제 문서는 실행환경을 "8개 서비스 그룹"으로 적는데 샘플 PDF 기준으로 만든 기존 테스트 질문은 "다섯 가지"였습니다. 둘을 같이 두면 모델이 두 근거를 섞으므로 샘플 PDF는 문서 폴더에서 빼냈습니다.

## 2. 적재할 때 고아 기록 정리

샘플 PDF를 폴더에서 빼도 `vector_store`의 청크 17개는 남습니다. 폴더와 DB가 어긋나는 구조적인 구멍이었습니다.

`IngestService.forget()`은 이미 있었지만 **호출하는 곳이 없는 죽은 코드**였습니다. 개별 삭제 API를 만드는 대신 `ingestAll`이 적재 전에 폴더 기준으로 DB를 맞추게 했습니다.

```java
// 폴더가 기준이다. 폴더에서 사라진 파일을 먼저 걷어낸 뒤 적재한다.
List<FileIngestResult> results = new ArrayList<>(removeOrphans(targets));
```

파일을 지울 때마다 사람이 따로 API를 부를 필요가 없어졌습니다. `Status.REMOVED`를 추가해 화면의 적재 결과에 그대로 표시됩니다. 대상 파일이 하나도 없으면 `ingestAll`이 그 전에 빠져나가므로 경로를 잘못 잡아 전부 지워지는 일은 없습니다.

## 3. 제목 기준 청킹 (이번 단계의 핵심)

실제 문서를 넣었는데도 "연계통합 레이어가 제공하는 서비스를 모두 알려주세요"에 Naming Service가 빠졌습니다. top-k를 3에서 5로 올려 정답 조각을 프롬프트에 넣어도, 답변 모델을 7.8b·9b로 키워도 고쳐지지 않았습니다.

조각 전문을 보니 원인이 분명했습니다.

```
조각 [4]  ### 연계통합          ← 제목은 있는데 항목이 1개
          - Naming Service

조각 [1]  - Web Service         ← 항목은 있는데 제목이 없음
          - Integration Service
          ### 배치처리           ← 바로 다음 절로 넘어감
```

`### 연계통합` 절이 첫 항목 바로 뒤에서 잘렸고, 이어지는 조각은 **자기가 어느 절 소속인지 알려주는 정보를 잃었습니다.** 모델이 확신할 수 있는 항목은 Naming Service 하나뿐이었습니다. 큰 모델이 오히려 하나만 답한 것은 더 신중했기 때문입니다.

그래서 청킹을 두 가지로 바꿨습니다.

1. **제목으로 먼저 절을 나눈 뒤** 각 절을 250토큰으로 자릅니다. 짧은 절은 통째로 한 조각이 됩니다. 연계통합 절은 276자라 한 조각에 들어갑니다.
2. **모든 조각 앞에 제목 경로를 붙입니다.**

```
[표준프레임워크 실행환경 소개 > 실행환경 서비스 구성 > 연계통합]
연계통합 레이어는 타 시스템과의 연동기능을 지원한다.
- Naming Service: ...
- Web Service: ...
- Integration Service: ...
```

제목이 없는 문서(PDF 등)는 경로가 빈 절 하나가 되어 기존과 똑같이 동작합니다.

| | 이전 | 이후 |
| --- | --- | --- |
| 1위 점수 | 0.579 | **0.718** |
| 답변 | Naming 누락 | **세 서비스 전부** |
| 청크 수 | 293 | 411 (전부 제목 경로 있음) |

청킹을 바꿨으므로 `/api/ingest?force=true`로 전체 재적재가 필요합니다.

## 4. 평가 질문 10개와 검색 개수

감이 아니라 숫자로 판단하려면 질문이 고정돼 있어야 합니다. 유형을 섞어 10개를 만들고 기대 답변까지 문서에서 확인해 [평가_질문.md](평가_질문.md)에 적었습니다.

| 유형 | 개수 | 무엇을 보는가 |
| --- | --- | --- |
| 단일 조각 | 4 | 기본 검색·답변 |
| 여러 조각에 흩어짐 | 2 | top-k가 넉넉한지 |
| 주제는 맞지만 답 없음 | 2 | 프롬프트가 막는지 |
| 주제가 다름 | 1 | 임계값이 막는지 |
| 전제가 틀림 | 1 | 문서로 바로잡는지 |

이 세트로 재면서 **top-k를 3 → 8로 올렸습니다.** ID 생성 방식을 묻는 질문에서 Table Id Generation이 7위(0.563), 세 방식 요약 조각이 8위(0.562)라 5로는 구조적으로 못 잡았습니다. top-k 6·7도 재봤지만 둘 다 세 방식을 다 내지 못했습니다.

**임계값 0.40은 그대로 유지합니다.** 관련 질문이 0.52~0.73, 주제가 다른 질문은 검색 0건이라 구간이 깨끗하게 갈립니다.

최종 결과는 **10개 중 9개 통과**입니다. 남은 실패는 "전제가 틀림" 하나이고, "답 없음" 2개는 "문서에서 찾을 수 없습니다"를 내지만 앞에 설명을 덧붙입니다(기능상 문제는 없음).

## 5. 화면 개선

| 개선 | 내용 |
| --- | --- |
| 근거 전문 모달 | 목록의 발췌는 200자에서 잘립니다. 근거를 누르면 네이티브 `<dialog>`로 전문을 띄웁니다. 서버가 `SourceRef.text`로 원문을 함께 내려줍니다 |
| 이전·다음 고정 | 근거 머리글을 `position: sticky`로 두어 목록을 내려도 버튼을 계속 누를 수 있습니다 |
| 답변 시간 | 제목에 `답변(34초)`처럼 표시합니다. 화면에서 째깍이던 경과 초와 같은 기준 시각을 씁니다 |
| 초기화 버튼 | 입력창을 비우고 커서를 옮깁니다 |

검색 결과가 0건일 때의 동작도 바꿨습니다. 이전에는 상태 문구만 뜨고 답변 칸이 비어 있어 "질문이 안 된다"처럼 보였습니다. LLM은 계속 건너뛰면서(수십 초 절약) 답변 칸에 "문서에서 찾을 수 없습니다"를 표시합니다.

모달 본문은 `textContent`로 넣어 HTML이 실행되지 않게 했습니다.

## 6. 해보고 되돌린 것

실패한 시도도 기록해 둡니다. 근거가 없으면 몇 달 뒤에 같은 실험을 또 하게 됩니다.

| 시도 | 결과 |
| --- | --- |
| 틀린 전제를 바로잡는 규칙을 **시스템 프롬프트**에 추가 | 효과 없음 |
| 같은 규칙을 **질문 바로 뒤**(생성 직전)로 이동 | 효과 없음 |
| **조각 순서 뒤집기** (1위를 질문 바로 앞에) | 목적은 미달, 다른 질문이 나빠져 되돌림 |
| **`temperature` 0.2 → 0.0** | 정확도·시간 동일, 재현성도 확보 안 됨 |
| **모델 교체** (`exaone3.5:7.8b`, `gemma2:9b`) | `gemma2:9b`는 맞히지만 457초라 쓸 수 없음 |

"전제가 틀림" 질문은 이렇게 다섯 가지를 시도해도 고쳐지지 않았습니다. `gemma2:9b`가 맞혔으므로 모델 크기의 한계가 아니라 `exaone3.5` 계열의 성향입니다. 이 질문은 이제 **모델을 교체했을 때 개선 여부를 재는 지표**로 남겼습니다. 실사용 대응은 질문을 중립적으로 쓰는 것입니다 — "다섯 가지 서비스 그룹이 뭔가요?" 대신 "몇 개의 서비스 그룹으로 구성되나요?"로 물으면 같은 조각으로 8개를 정확히 답합니다.

## 7. 배운 점

**조각은 내용뿐 아니라 맥락을 들고 있어야 한다.** 목록이 조각 경계에서 잘리면 뒷조각은 소속을 잃습니다. 이 상태에서는 top-k를 올려도, 모델을 키워도 고쳐지지 않았습니다. 제목 경로를 붙이는 것만이 해결이었습니다.

**측정값은 한 번 재서 믿으면 안 된다.** 같은 질문을 같은 설정으로 3회 돌렸더니 13초에서 72초까지 벌어졌고, 답변 길이와 역방향이었습니다. Ollama가 같은 프롬프트의 앞부분 계산을 재사용하기 때문입니다. **회차가 다른 개별 질문의 시간을 비교하면 안 됩니다.** 정답 여부도 흔들립니다 — ID 생성 질문은 10회 중 9회만 맞았습니다. `temperature`를 0으로 내려도 9개 중 4개만 두 번 실행에서 같았습니다. 이 환경의 비결정성은 온도가 아니라 CPU 추론의 계산 경로에서 옵니다.

**속도의 한계는 장비에 있다.** GPU가 없어(Intel 내장 그래픽은 Ollama가 쓰지 못함) 순수 CPU 추론이고, 초당 3~5토큰입니다. 답변에 40~170초가 걸리는 것은 정상입니다. 무료로 줄일 방법은 답변을 짧게 유도하기, `OLLAMA_KEEP_ALIVE` 늘리기 정도이고, 체감을 바꾸는 가장 효과적인 수단은 SSE 스트리밍입니다.

**잘못된 가설도 빠르게 버려야 한다.** 이번에 세운 가설 중 "조각 개수를 늘려도 시간 비용은 작다", "`temperature` 때문에 불안정하다", "`num-ctx` 4096을 넘겨 잘린다"는 모두 측정으로 틀렸음이 드러났습니다. 마지막 것은 프롬프트가 1,534토큰(여유 2,562)이어서 애초에 성립하지 않았습니다.
